# v1.4.0 — Library and account work plan

The work plan for the `v1.4.0` entry in [ROADMAP.md](ROADMAP.md) and its `v1.4.1`–`v1.4.3`
follow-up patches: moving GOG metadata out of widget state and into providers, a faster library
with a refresh, keeping the selected game across nav tabs, update detection, installing and
removing DLC on an installed game, and signing out. Each phase below should fit in one short
session and end with a green `fvm flutter analyze --fatal-infos` and `fvm flutter test`, plus one
commit. Phase 5 is the exception: it happens in the dependency repos, not here.

Tick each checkbox as it's done. If a phase turns out bigger than one session, split it here before
starting, not halfway through.

## Branching

`main` is protected (see [CI-CD-WORKPLAN.md](CI-CD-WORKPLAN.md)): nobody pushes to it, and every change
lands through a merge request. This release has no long-lived branch. Each group of phases gets a
short-lived branch and one MR, merged semi-linearly, with the source branch deleted on merge.

- **MR grouping** (proposal): Phases 1–4; Phases 5–6, once the bridge is tagged; Phases 7–9. Each MR
  leaves `main` releasable. `pubspec.yaml` stays at `1.3.0` until Phase 9.
- Each phase is still one commit on the MR's branch, so the merge commit shows the phases underneath.
  Use squash only for an MR whose branch has red or revert commits.
- The MR pipeline replaces the old pre-release `rc` tag: it runs lint, test and scan on the branch.
  Still run `analyze` and `test` locally every phase.
- Phase 9 tags `v1.4.0` on `main`'s merge commit after its MR merges.
- The patches (P1–P3) are one MR each, or one MR for all three with a tag per merge commit. Tag on
  `main`'s merge commit after the merge.
- A `v1.3.x` hotfix is the only case that uses the cherry-pick path described under "Decisions" in
  CI-CD-WORKPLAN.md.
- While Phase 5 is in progress, `pubspec.yaml` may point `gogdl_flutter` at a branch `ref`. It must be
  back on a **tag** before Phase 6's commit. The lockfile's `resolved-ref` is what CI builds against. If
  the bridge's Rust pin changes, bump the CI image tag in `.gitlab-ci.yml` in the same commit.

## Dependency changes

Everything v1.4.0 needs from `gogdl_flutter` (pinned at `v1.3.0`) and `gogdl-lib` (pinned by the
bridge at `v1.2.3`), found by reading both at those tags. Phase 0 confirmed the open assumptions and
added D3; Phase 5 implements the list. D1 blocks DLC removal, D3 blocks a refresh that shows new data.

| D3 | gogdl-lib, gogdl_flutter | **Clear the cache.** `GogDl::clear_cache()` drops the per-instance memoized owned products, game builds and downloadable products (leave details, links, summary and screenshots: they don't change). **What doesn't need a dependency change**, and why:
- **Providers, parallel titles, the selected game (A, B-titles, C).** All pure Lumen: every call
  they need already exists on `GogBackend`. The library *refresh* needs D3 to see new data.
- **Installing DLC on an installed game (F, install half).** `repair_game` with the new, larger
  product set downloads only the missing chunks, the same way it resumes a download.
- **Update detection (E).** `get_game_builds` already returns each build's `build_id`,
  `version_name` and `release_date_timestamp` (D3 only matters for builds published after launch). Applying an update is the existing Builds-tab
  "Switch" flow (`startRepairForInstalled`).

**Release order for the deps:** gogdl-lib first (D1's core and D3), tagged as that repo's next version.
Then gogdl_flutter pins that tag, exposes D1 and D3, and gets its own next tag. Lumen
pins the bridge tag in Phase 6.

## Ordering rationale

- The investigation (Phase 0) comes first. Update detection and DLC removal depend on facts about
  GOG's data that aren't in either repo: how builds are ordered, whether a version name can repeat,
  whether unowned DLC shows up in `get_downloadable_products`, and whether a fresh `GogdlApi` after
  sign-out really starts unauthenticated. (Answers are in the session log. It also found the cache
  behind D3.)
- Providers (Phase 1) go before everything else in the library. Parallel titles, refresh, update
  detection and the DLC tab all read metadata, and each would otherwise add one more
  `addPostFrameCallback` fetch to rewrite later.
- Titles and refresh (Phase 2) build directly on Phase 1's providers: a refresh is an invalidation.
- The selected game (Phase 3) is small and independent. It comes after Phase 2 because both edit
  `library_page.dart`.
- Sign out (Phase 4) comes before the dependency work so the no-dependency items are all done while
  Phase 5 is in progress. It also needs Phase 1: signing out has to drop every cached provider, and
  that's one invalidation instead of hunting down widget-level caches.
- The dependency work (Phase 5) and adopting it (Phase 6) come before DLC removal.
- Update detection (Phase 7) comes before DLC (Phase 8). Both change what an installed game's
  Builds and DLC tabs offer and both start repairs on installed games. Update detection is the
  simpler one, so it settles the "change an installed game" confirm-and-repair pattern that Phase 8
  then reuses.
- DLC (Phase 8) comes last: it's the only item that can slip. If D1 stalls, ship DLC install only
  and move removal to a `v1.4.x` patch, without holding the rest back.

## Phase 1 — Metadata providers

Files: new `lib/state/library_state.dart`, `lib/state/gog_state.dart`,
`lib/screens/home/pages/library/{library_page,overview_tab,builds_tab,products_tab}.dart`,
`lib/screens/home/pages/settings/proton_manager.dart`, `lib/components/game_action_buttons.dart`
(`_preload`), tests.

Metadata lives in widget `State` today, fetched with `addPostFrameCallback`, so it's lost on every
tab switch and each screen hand-rolls its own loading/error/Retry.

- [ ] `library_state.dart`: `ownedGamesProvider` (`FutureProvider<List<int>>`), and families
  `gameTitleProvider(gameId)`, `gameSummaryProvider(gameId)`, `gameScreenshotsProvider(gameId)`,
  `gameBuildsProvider(gameId)`, `gameProductsProvider((gameId: …, buildName: …))` and
  `protonReleasesProvider(page)`. Each gets an explicit `name:`. They read
  `ref.watch(gogStateProvider)`, so overriding `gogBackendProvider` in tests still works.
- [ ] Error contract: `GogState` returns `null` on failure. Each provider turns `null` into a thrown
  error, so the UI gets `AsyncError` (and an empty list stays a real `AsyncData([])`). Summary and
  screenshots currently return `''`/`[]` on failure; keep that (an empty summary isn't worth an
  error state).
- [ ] **Decide who caches** (your call; recommended first):
  - (a) **Recommended.** The providers do. Drop `GogState._ownedGamesCache`, `_gameNameCache` and
    `invalidateOwnedGames` (the providers aren't `autoDispose`, so they live for the session and
    `ref.invalidate` is the refresh). Keep the boxart/background Future caches: `GameCard` and the
    hero banners feed them to `FutureBuilder`s, and moving those is churn with no user-visible
    gain. Update the "Names, boxart and background links" doc comment.
  - (b) Keep both. Simpler diff, but a refresh then has to clear two layers, and the next reader
    won't know which one is the truth.
- [ ] Keep `GogState.getOwnedGames`'s sort, and its rule that an empty result isn't cached: with
  (a), `ownedGamesProvider` doesn't cache an empty list either (invalidate itself, or treat `[]` as
  data but let Retry invalidate; pick one and comment why).
- [ ] **Riverpod 3's automatic retry:** a failed provider retries on its own with backoff, which
  would hammer GOG while the user stares at an error, and makes widget tests pump forever. Set
  `retry: (_, _) => null` on these providers (or once on the `ProviderScope`/`createContainer()`,
  if that reads better) so Retry is always explicit. *(Phase 0: 3.3.2's `defaultRetry` retries any
  non-`Error` exception up to 10 times, 200 ms doubling to 6.4 s. Decision: a shared constant in
  `library_state.dart` passed to each provider, not a container-wide setting.)*
- [ ] Rewire the screens to `ref.watch(...)` + `.when(...)`: library grid, Overview, Builds (keep
  its Refresh chip, now `ref.invalidate(gameBuildsProvider(gameId))`), DLC tab, the Proton releases
  dialog's pages, and `GameActionButtons._preload`. No behavior change beyond "no refetch on tab
  switch". The DLC tab's side effect (auto-adding `GAME` products to the config) moves out of
  `build` into a `ref.listen` or stays in a post-frame callback; it must not run on every rebuild.
- [ ] Update CLAUDE.md's `GogState` paragraphs (owned-games caching now lives in providers).
- [ ] Tests: each provider's success, failure (→ `AsyncError`) and invalidate-refetches;
  `FakeGogBackend` call counts show a second watch doesn't refetch; existing Library/Builds widget
  tests pass with their error and empty states unchanged.

**Done when:** switching between a game's tabs and back doesn't refetch, `grep -rn
addPostFrameCallback lib/screens` only finds non-fetch uses, and the tests are green.

## Phase 2 — Parallel titles and library refresh

- [ ] Search keeps matching on titles, as today. A game whose title hasn't loaded keeps today's

- [ ] **Decide whether refresh also invalidates cached successful titles** (recommended: no; titles

- Concurrency bound: **8** (Phase 0: 9 titles took 4.0 s serially and 0.55 to 1.8 s at 4 to 16 in

- [ ] Tests: with a fake that delays titles, all requests are in flight up to the bound (count
  concurrent calls); a failed title leaves the others shown; refresh picks up a game added to the

Files: `lib/screens/home/pages/library/products_tab.dart`, `lib/state/downloads_state.dart`,
`lib/state/games_state.dart`, tests.

Toggling a product on the DLC tab only changes the stored set, and nothing downloads until a manual
repair. The tab also has no empty state, and its label ("Select all products to download") is
unclear.

- [ ] **Not installed:** keep today's behavior (the toggles pick what the install will download),
  with a clearer label: "Choose which DLC to install with the game".
- [ ] **Installed:** toggles no longer write the config directly. They build a pending selection,
  and an "Apply changes" bar appears ("Install 2 DLC · Remove 1 DLC", with sizes from
  `getInstallSize` where it's cheap) with Apply and Discard.
- [ ] Apply, in `DownloadsNotifier` (a new method, not the widget):
  1. Removals first, if any: `GogState.removeProducts(keep: new set, remove: dropped ids)`. A
     failure stops here with the error shown, and the config keeps the old set.
  2. Additions, if any: a repair with the new product set (`startRepairForInstalled`), shown on the
     Downloads page as today. Update the config's product set only when the repair succeeds, so a
     failed or cancelled one can be retried without the UI claiming the DLC is installed.
  3. Removals only: update the config right after step 1.
  Refused while a job runs for the game or the game is running.
- [ ] The `GAME` product can never be deselected (it isn't shown, as today, and Apply asserts it's
  in the set).
- [x] Unowned DLC: nothing to do. Phase 0 found `get_downloadable_products` filters to owned products

  Listing products costs one `get_product_details` request each, sequentially: 1.0 s for 3
  products, 2.5 s for 8. It's cached per provider, so show the loading state and don't refetch per

- [ ] DLC tab UX (GAPS §6): an empty state ("This game has no DLC") with the loading and error

- [ ] **If D1 slipped:** ship install only. Removal toggles on an installed game are disabled with

  added below.
- [ ] Tests: installed + add → `repairDownload` with the larger set, config updated only on success;
  installed + remove → `removeProducts` with the right keep/remove sets, then config updated; a
  failed removal leaves the config alone; mixed → removal then repair; not installed → toggles still
