# Devlog — v1.6.0 Distribution

Releases users can actually reach (GitHub, not the self-hosted GitLab) and an AppImage that updates
itself in place — the `v1.6.0` ROADMAP entry. The AUR package was part of it until Phase 0 found AUR
account registration closed; it was deferred, so the release ran as Phases 0–4 on 2026-10-17. Pipeline
and packaging work only: the one new Dart file is a release tool, and the app itself didn't change.
Kept here for the decisions and pitfalls that aren't obvious from the diff. Ended at 537 passing tests
and `flutter analyze --fatal-infos` clean (baseline 506).

There was no long-lived release branch; `main` is protected, so each group of phases was its own MR.
SHAs are on `main`: Phases 0–2 were MR !34, squashed to `23d3f65` (merge `6c7df3d`); Phase 3 committed
nothing; Phase 4 was MR !35, `4419d7f` (merge `4ab2fe2`, tagged `v1.6.0`). The work plan was deleted
with this devlog.

## Phase 0 — Investigation

**zsync.** `appimagetool` 1.9.1 bundles `zsyncmake`, so `-u "gh-releases-zsync|…"` produces the
`.zsync` with nothing new to pin, and it works without FUSE under `APPIMAGE_EXTRACT_AND_RUN=1`. **Trap:**
it writes `<out>.zsync` into the current directory, not beside the AppImage. The `.zsync`'s
`Filename:` and `URL:` are the bare AppImage name, so it resolves next to the `.zsync` on GitHub.

**GitHub.** The push mirror showed no measurable delay on the `v1.5.x` tags. The repository has
*immutable releases* on, which ruled out GAPS's "`--clobber` on a re-run": a published release's
assets can never change. The "Protect main" and "Protect tags" rulesets only restrict deletions and
force pushes, so neither blocks a release on an existing tag.

**The release tool.** There is no official `gh` container image, and the CI image has `curl` but no
JSON parser, so the tool is `tool/github_release.dart` on `dart:*` only (an `HttpClient` against the
REST API), unit-tested through injected seams like `tool/osv_gate.dart`. Nothing new in
`pubspec.lock`, no new image, and the same tool runs locally. Its token is a separate fine-grained
one (`Contents: read and write` on `lumen`, 90 days), so rotating it never breaks the mirror's.

**AUR, deferred.** `lumen` is taken by an unrelated Rust CLI, so the name was `lumen-gog-bin`. A
`makepkg` spike in a digest-pinned `archlinux:base-devel` worked (`--appimage-extract` in `prepare()`
needs no FUSE; base-devel has no `git` or `ssh`), and namcap was quiet on a settled `depends` list.
Then account registration turned out to be closed with no date to reopen, so the package moved out of
the release; every finding lives in GAPS §4 "AUR package". The same namcap run found a build-host
`RUNPATH` in `libflutter_secure_storage_linux_plugin.so`, which ships in every AppImage (GAPS §4).

## Phase 1 — AppImage update information

`tool/build_appimage.sh` keeps the update string in one `update_info` variable beside the pinned
tools (a local build gets the same string; a dev build that "updates" to the latest release is fine),
runs `appimagetool` from `build/appimage` so the `.zsync` lands beside the AppImage, and fails if it is
missing. `package` keeps three artifacts, `publish` uploads three and exports `ZSYNC_URL`, `release`
links three. **Trap:** `--appimage-updateinformation` under `APPIMAGE_EXTRACT_AND_RUN=1` hands the flag
to the app and starts it, so the check runs without it, and CI reads the `.upd_info` ELF section with
`objcopy` instead.

**Push options.** Every MR is opened by the push that publishes its branch
(`-o merge_request.create …`), since a branch without an MR gets no pipeline. Git refuses a newline in
a push option, so the push carries a one-line description and the full one is pasted in the UI.

## Phase 2 — The `github-release` job

**Mirror wait in the tool**, not a shell step, so the dry run and the backfill exercise it too: it
polls `git ls-remote` (the peeled `^{}` line first, for an annotated tag) every 10 s for up to 5 min,
and fails at once if GitHub's tag points anywhere but `CI_COMMIT_SHA`.

**Idempotency under immutable releases.** Drafts are only visible through the paginated release list,
not the by-tag endpoint, so that is how a release is found; two releases for one tag fail. No release:
create a draft, upload the three files, check the draft's assets (name, size, `state`, and GitHub's
`sha256:` `digest`), then publish — once published, nothing can be fixed. A leftover draft gets its
assets replaced and the same check. A published release is only compared: a match succeeds with no
writes, a difference fails.

**"Latest"** is `true` only when the tag is the highest `vX.Y.Z` among published releases, so an
older-minor hotfix never becomes the release the `gh-releases-zsync|…|latest|…` string points at.

**Dry run.** Protected variables don't reach MR pipelines, so `github-release-dry-run` runs with no
token, only GETs, and refuses any write in code. It rehearses the latest GitLab tag: that tag's own
`release_notes.sh` (in a worktree) and the files `publish` uploaded to the registry (`.zsync` optional,
since older releases have none). A 401/403 (or 404 on a write) fails with a message naming the token's
permission, and the `Authorization` header is redacted from any error. 31 tests. The token, the
`github-release` environment and the masked, protected variable were created after the merge
(expires 2027-01-15, GAPS §5).

## Phase 3 — Backfill `v1.5.2`

The tool's first real write went to a release nobody depended on yet, run by hand: `v1.5.2`'s
AppImage and `.sha256` from the GitLab release (two assets, no `.zsync`), notes from
`release_notes.sh` at the tag, a dry run first, then the real run with the token read by `read -rs`
(never on a command line). A second run was a no-op. The GitHub copy is byte-identical to GitLab's,
immutable and "Latest", which also gave the first CI run a real list to compute `make_latest` against.
`v1.5.0` and `v1.5.1` were not backfilled: they would sit below `v1.5.2` and add nothing users need.

## Phase 4 — Release

README "Installing" now downloads from the GitHub release, with a new "Updating" section; README,
SECURITY.md and CLAUDE.md say the GitHub mirror also carries the releases; GAPS took the AUR findings.
The `v1.6.0` tag pipeline was green on `github-release`'s first CI run: the mirror wait passed at
`4ab2fe2`, and the release is "Latest" and immutable with the AppImage, `.sha256` and `.zsync`. The
AppImage downloaded from GitHub passes its `.sha256` and prints its update information, and the
`.zsync`'s `Filename:`, `URL:` and `Length:` match it.
