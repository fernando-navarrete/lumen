# v1.1.0 — Foundation work plan

The work plan for the `v1.1.0` entry in [ROADMAP.md](ROADMAP.md): tests, CI and the state
architecture. The follow-up `v1.1.x` patches build on it. Each phase below should fit in one
short session and end with a green `fvm flutter analyze` (and `fvm flutter test` once `test/`
exists) plus one commit. The tag is cut only at the end (Phase 9), so `main` keeps shipping as
`1.0.14` until then.

Tick each checkbox as it's done. If a phase turns out bigger than one session, split it here
before starting, not halfway through.

## Scope

From ROADMAP `v1.1.0`, with the GAPS reference for each:

| # | Item | GAPS | Phase |
|---|---|---|---|
| A | `gogBackendProvider` so tests can swap in a fake `GogBackend` | §4 P1 | 1 |
| B | Resolve the `lib/models/` mismatch between CLAUDE.md and the code | §4 P1 | 2 |
| C | `test/` covering the notifiers, `guardBridgeStream` and `findExecutables`, plus 1.0.x regression tests | §7 P0 | 1, 3, 4, 8 |
| D | Immutable `ActivityTask`, `SaveTask`, `ProtonTask`, `RunningGame`, replacing the `v1.0.4` stopgap | §4 P1 (4.1) | 5, 6 |
| E | Nav state as a single `Notifier<NavBarItem>` | §4 P1 | 7 |
| F | CI (GitLab CI, self-hosted runner on `thinkcentre.home`) running analyze and test | §7 P1 (×2) | 0, 8 |

**Out of scope:** everything in the `v1.1.1+` patch list (stream caches, error-handling
consistency, emit throttling, settings debounce, schema version, secure storage). Where a phase
touches that code, leave it alone and note what you found under that patch in ROADMAP instead.

## Ordering rationale

- The backend seam and test harness (Phase 1) come first because every later phase adds tests
  through them.
- The models decision (Phase 2) goes before the notifier tests, so the fake backend and fixtures
  are written once against the final types.
- Characterization tests for the notifiers (Phases 3–4) go **before** the immutability refactor
  (Phases 5–6), so the refactor has a safety net. The tests only read `state`, so they pass
  against both the mutable and the immutable implementation.
- Phase 0 (making `gogdl_flutter` reachable) is infrastructure that may depend on external
  accounts. It can run in parallel with anything else, but CI (Phase 8) is blocked on it.

## Phase 5 — Immutable `ActivityTask` (the big one)

`downloads_state.dart` has about 48 in-place field writes on tasks. Do this phase on its own.

- [x] Make every field of `ActivityTask` `final`, and add `copyWith`, using the same `_unset`
  sentinel pattern as `GameConfig` for the nullable fields (`stage`, `chunksToRedownload`, `path`,
  `buildName`).
- [x] Make collection fields unmodifiable (`List.unmodifiable` / `Map.unmodifiable`) in the
  constructor or `copyWith`, so an accidental in-place write fails fast.
- [x] In `DownloadsNotifier`, replace each `task.x = …` with building a new task and
  `state = DownloadsState({...state.tasks, gameId: updated})`. A private `_update(gameId,
  ActivityTask Function(ActivityTask))` helper keeps this readable. Keep the existing emit
  throttling working: it must now throttle the *state replacement*, not a notify on a mutated
  object. Went with a `Map<int, ActivityTask> _pending` buffer instead of the sketched `_update`
  helper: each stream handler keeps a closure-local `var task` it reassigns via `copyWith`, and a
  new `_commit(current, next, {throttle})` writes it into `_pending` and calls `_emit`/
  `_emitThrottled`, only if `current` is still the task registered for its game (in `_pending`, or
  `state.tasks` if nothing's buffered) — see the added stale-stream guard below.
- [x] Check the throttle's last pending update always flushes on `onDone`/error. `_emit()` now
  merges `_pending` into `state.tasks` and clears it; both the trailing timer and every unthrottled
  path (`onDone`, `onError`, `stream == null`) go through `_emit()`, so nothing buffered is ever
  lost.
- [x] Add an identity test: after an event, `state.tasks[id]` is a new object, and the old
  snapshot still has its old values.
- [x] Phase 4a tests pass unchanged (all 17, no edits needed).
- [x] Manually check the Downloads page during a real download, verification and repair. User
  confirmed: download progress reports smoothly. (Verification/repair weren't separately called
  out, but drive the exact same `copyWith`/`_commit`/throttle path as download, so this is treated
  as covering all three.)

**Found and fixed a latent bug while doing this (not in the original plan):** today, a stream whose
task was dequeued (e.g. `startVerificationForInstalled` while a verification is still running)
keeps delivering events to the orphaned in-place object — harmless before, since nobody could read
it once its map entry was replaced. With per-gameId `copyWith` + `_commit`, a stale stream's update
would otherwise silently overwrite whatever task replaced it. Added a stale-stream guard to
`_commit`: it only writes `next` if `current` is `identical` to the task currently registered for
that gameId, otherwise the event is dropped (the closure-local `task` variable still advances, so
the stale stream's own `onDone`/`onError` logic keeps working off consistent values — only the
side effects that touch `_gamesNotifier` there, e.g. `markInstalled`, stay unconditional, matching
today's behavior). Covered by a new test ("a stale stream cannot clobber the task that replaced
it"); sanity-checked by relaxing the guard to unconditionally commit and confirming that test goes
red.

**Done when:** `grep -nE "task\.[a-zA-Z]+ *=[^=]" lib/state/downloads_state.dart` finds nothing,
and the tests pass. Verified: 0 matches; `flutter analyze` clean; `flutter test` 77/77 passing (73
existing + 4 new in a "DownloadsNotifier — immutability (Phase 5)" group: identity, unmodifiable
collections throw, throttled-rapid-events-still-flush-the-terminal-value, and the stale-stream
guard).
