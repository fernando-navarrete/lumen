# Devlog — v1.4.0 Library and account

Metadata moved out of widget state into providers, a faster library with a refresh, the selected game
kept across nav tabs, sign out, update detection, and installing and removing DLC on an installed
game — the `v1.4.0` ROADMAP entry — plus the `v1.4.1`–`v1.4.3` patches that followed it. Ran as
phases 0–9 and three patches over 2026-09-26 to 2026-10-13, with Phase 5 done in the dependency
repos. Kept here for the decisions and pitfalls that aren't obvious from the diff. Ended at 450
passing tests and `flutter analyze --fatal-infos` clean.

There was no long-lived release branch; `main` is protected, so each group of phases was its own
MR, merged semi-linearly. SHAs are the merge commits on `main`: Phases 1–6 `99a414c`, Phase 7
`d05203e`, Phase 8 `e4d0eb9`, Phase 9 `18ab703` (tagged `v1.4.0`), then one MR per patch: `5420fa5`
(`v1.4.1`), `8e09898` (`v1.4.2`), `577c203` (`v1.4.3`). The work plan was deleted with this devlog.

## Phase 0 — Investigation

Probed with a scratch Rust bin on gogdl-lib `v1.2.3` (9 owned games). Baseline was 357 tests.

**Builds.** Newest-first (matches `date_published`), 1 to 10 per game, no repeated `version_name` or
`build_id`, Windows only (`os/windows/builds`), no branch field. So update detection matches on
`versionName` and needs no schema bump. Re-check if a game with many builds turns up.

**DLC listing.** `get_downloadable_products` filters to owned products, so unowned DLC never shows
up (the first assumption was the opposite). One `get_product_details` request per product,
sequentially: 1.0 s for 3 products, 2.5 s for 8.

**DLC files.** The downloader never deletes files (`remove_file`/`remove_dir*` exist only in the
Proton and saves code), so repairing with fewer products leaves the DLC on disk. That motivated D1.
Five of Alien: Isolation's seven DLCs share 9 files each with the base game
(`DATA\TEXT\<LANG>\DLCnn_FRONTEND.TXT`), so removal must keep files listed by `keep`, compared
case-insensitively on normalized paths. No live repair run: both DLC games are 30 GB+.

**Sign out.** A fresh `GogDl` with no `restore_auth` fails `get_owned_games` with
`NotAuthenticated`, and there is no global auth state, so `ref.invalidate(gogBackendProvider)` is
enough. D2 (a bridge `sign_out`) was dropped.

**Titles.** 9 titles: 3.99 s serially, 1.38 s at 4 in flight, 1.76 s at 8, 0.55 s at 16 (noisy, tiny
library). Bound: 8.

**Riverpod 3.3.2 retries.** `defaultRetry` retries non-`Error` exceptions up to 10 times (200 ms
doubling to 6.4 s), which would hammer GOG behind an error screen and hang widget tests. Every
library provider passes the shared `noRetry`; Retry is always an explicit invalidate.

**The cache nobody expected.** gogdl-lib memoizes owned products (re-fetched only while empty),
game builds and downloadable products per `GogDl` instance, so `ref.invalidate` alone re-read the
same list: a game bought after launch never appeared, and the Builds tab's Refresh chip had always
been a no-op. That added D3 (`clear_cache`). Phase 2 was built with a no-op seam first and wired to
it in Phase 6.

## Phase 1 — Metadata providers

`lib/state/library_state.dart`: `ownedGamesProvider` plus families for title, summary, screenshots,
builds, products (keyed by `(gameId:, buildName:)`) and Proton release pages. **Caching decision:**
the providers cache and are not `autoDispose`; `GogState` dropped its owned-games and title caches
and keeps only the boxart/background Futures, which the cards feed straight to `FutureBuilder`s.
A `GogState` `null` becomes a thrown `MetadataUnavailableError`; summary and screenshots keep
`''`/`[]` on failure.

Dropping the name cache meant the Downloads cards, game header and dialogs read titles through
`gameTitleProvider` or the one-shot `readGameTitle` too. The Proton dialog watches pages `1.._pages`
and `ProtonNotifier.fetchReleases` went away. `_BuildsMessage` became
`components/retry_message.dart`, reused by the DLC tab's new error state. The DLC tab's GAME
auto-add is a `listenManual` registered post-frame, so it doesn't run on every rebuild.

## Phase 2 — Parallel titles and library refresh

No separate `libraryTitlesProvider`: `gameTitleProvider` itself runs through a shared 8-wide
`AsyncLimiter` (`lib/common/async_limiter.dart`), so the grid, header and dialogs share one bound
and one cache, and the grid fills in per title. Later (Phase 7) the same limiter, renamed
`metadataFetchLimiterProvider`, also bounds builds.

`LibraryRefresher.refresh()` clears the backend cache, invalidates only the titles that failed
(loaded ones don't change and refetching them is the slow part), then the owned list. The grid keeps
its previous data meanwhile, with a spinner on the chip (`RefreshChip` extracted to `components/`);
a failed refresh shows a snackbar. `FakeGogBackend.delayOn` holds calls open for tests.

## Phase 3 — Keep the selected game across nav tabs

`librarySelectionProvider` (`({int gameId, SelectedTab tab})?`, in `home_state.dart`, which `SelectedTab`
moved to) is the single source of truth, so the details tab survives too. It `ref.listen`s
`ownedGamesProvider` and clears the selection only when a *loaded* list lacks the game; loading and
errors keep it. Back and `onUninstalled` go through `clear`/`selectTab`.

## Phase 4 — Sign out

`Account.signOut` (`lib/state/account.dart`) keeps all local data (installed games, configs,
prefixes, Proton versions); the dialog says so. It refuses, naming what runs, while a download,
verification, repair, Proton download, save sync or game is running. Paused tasks don't count.

**Trap:** `DownloadsNotifier`, `SavesNotifier` and `ProtonNotifier` read `GogState` once in
`build()`, so invalidating `gogBackendProvider` alone left them on the disposed backend. Sign-out
invalidates them too, and that exposed the second trap: Riverpod reuses the `Notifier` instance
across rebuilds, so their `late final` fields threw `LateInitializationError` on the second
`build()`. They are `late` now. `createContainer(backendFactory:)` builds a new fake per backend
rebuild, like production.

## Phase 5 — Dependency work

Done in `gogdl-lib` (`v1.3.2`; `clear_cache` and `remove_products` shipped in `v1.3.0`) and
`gogdl_flutter` `v1.4.3`: `v1.4.0` has `clearCache()` and `removeProducts()` → `ProductRemoval`, and
`v1.4.1`–`v1.4.3` are additive (faster tolerant `getDownloadableProducts`, `getGameLinks`,
`getProtonReleasePage`). The Rust pin stayed 1.98.1, so no CI image bump. `removeProducts` stayed a
`Future` (6.9 s for one Alien: Isolation DLC). The bridge's own devlog says `clearCache()` wasn't
proven end to end, because its test game was a demo outside the owned list.

## Phase 6 — Adopt the new bridge

Pinned `v1.4.3` straight past `v1.4.0`–`v1.4.2`. `ProductRemoval` is an app-owned model, per the
rule that bridge data types get adapted. **Error convention differs on purpose:**
`removeProducts` logs and rethrows (the caller must tell the user why), `clearCache` logs and
swallows (a refresh should still refetch). The bridge exports `ProductRemoval`, so every `hide`
list in the app gained it. Not adopted: `getGameLinks`/`getProtonReleasePage` (GAPS §4 P2).

## Phase 7 — Update detection

`gameUpdateProvider(gameId)` is the newest listed build when an installed game's `selectedBuild` is
an older listed one. It is null while loading, on failure, for a game that isn't installed (which
never fetches builds), and when the installed build is delisted — that is the existing stale-build
note, not an update. One shared `latestBuild` helper serves it and `GameActionButtons`.

**Behavior change:** a build switch or update records `selectedBuild` only when its repair
succeeds (`_runRepair`), not at confirm, so a failed one keeps the old build and the badge. Update
skips the install space check, like Resume and Retry: the repair's pre-flight checks only the
changed files, and the full install size would mislead.

## Phase 8 — DLC on installed games

`DownloadsNotifier.applyProductChanges`: removals first through `GogState.removeProducts` (a failure
rethrows with the config untouched; success drops those ids at once), then a repair with the full
set for additions, whose ids are recorded only when it succeeds. It refuses while the game or a job
for it runs (`ProductChangeError`), and `GAME` products can never be dropped. The DLC tab keeps a
pending selection with Apply/Discard, confirms before removal, reports files and bytes freed,
offers Select all/none, has an empty state, and is locked while downloading or paused. For a game
that isn't installed the toggles still write the config.

No pre-Apply size estimate: `getInstallSize` fetches manifests per call, so it was not cheap.

## Phase 9 — Release

CLAUDE.md was re-read against the code and was already accurate, because each phase kept it up to
date; the games schema stays at 3. GAPS: sign out, refresh, providers and the selected game ticked;
sorting and the offline view split into their own open item.

## Patches

**`v1.4.1`: untitled games.** A loading title renders `GameCard.skeleton`; a failed or empty one
falls back to "Game `<id>`" with its boxart (counted, clickable, searchable), so an owned game never
silently disappears. The hero picks the first installed game with a loaded title, else the first
titled, else the first.

**`v1.4.2`: screenshots.** `AsyncCoverImage.decodeAtLayoutWidth` is opt-in: it reads the width from a
`LayoutBuilder` and sets `cacheWidth` = width × `devicePixelRatio`. That is only right for
width-bound `cover` images, so the hero and the Downloads thumbnails keep full decode. Used by the
screenshot grid (now `BoxFit.cover`) and `GameCard` boxart.

**`v1.4.3`: "Installing" filter.** `_LibraryFilter.installing` matches downloading and paused;
"Installed" is now `downloaded` only. The chip renders only while some owned game is installing, and
`_GameGridState.build` resets a selected-but-vanished chip to All. The card and Overview labels
already agreed. Tests build persisted `games` fixtures (each entry needs `selectedBuild`) and assert
on `GameCard`s, since the hero repeats the featured title.

## Not verified live

appearing after Refresh (D3 end to end), and DLC removal or install on a real install, were tested
