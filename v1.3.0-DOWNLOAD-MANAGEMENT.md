# v1.3.0 — Download management work plan

The work plan for the `v1.3.0` entry in [ROADMAP.md](ROADMAP.md): stopping, pausing and resuming
download jobs, cleaning up after them, uninstalling, and checking disk space before an install
starts. Each phase below should fit in one short session and end with a green
`fvm flutter analyze --fatal-infos` and `fvm flutter test`, plus one commit. Phase 2 is the
exception: it happens in the dependency repos, not here.

Tick each checkbox as it's done. If a phase turns out bigger than one session, split it here before
starting, not halfway through.

## Branching

Unlike `v1.2.0`, this release is built on its own branch, **`release/v1.3.0`**, cut from `main` at
`v1.2.5`. `main` stays at `1.2.5` until the release phase.

- Every phase commits to `release/v1.3.0`. Nothing merges to `main` before Phase 10.
- A hotfix needed in the meantime goes on `main` as a normal `v1.2.x` patch, following the ROADMAP
  rules. Then merge `main` into `release/v1.3.0` right away, so the two don't drift apart.
- CI only runs on tag pushes, so branch commits get no pipeline. Run `analyze` and `test` locally
  every phase, as before. To get CI on the branch before merging, push a pre-release tag
  (`v1.3.0-rc.1`) from it in Phase 10. Any tag triggers the pipeline.
- Phase 10 merges with `--no-ff`, so `main`'s history shows v1.3.0 as one merge with its phases
  underneath. Then it tags `v1.3.0` on `main`.
- While Phase 2 is still in progress, `pubspec.yaml` may point `gogdl_flutter` at a branch `ref` on
  `release/v1.3.0`. It must be back on a **tag** before Phase 3's commit. The lockfile's
  `resolved-ref` is what CI builds against.

## Dependency changes

Everything v1.3.0 needs from `gogdl_flutter` (the bridge, currently pinned at `v1.1.3`) and
`gogdl-lib` (pinned by the bridge at `v1.0.11`), found by reading both at those tags. Phase 0
confirms the open assumptions, and Phase 2 implements the list. Only D1–D5 block this release.

| # | Repo | Change | Why | Blocks |
|---|---|---|---|---|
| D1 | gogdl_flutter | **Cancellation for `download_game`, `verify_download` and `repair_game`.** Add an opaque `CancelToken` (wrapping `tokio_util::sync::CancellationToken`, via `#[frb(opaque)]`) with a sync `new()` and `cancel()`. Each of the three functions takes a `cancel: &CancelToken` and races its job against `token.cancelled()` in a `tokio::select!`. | Today each function `tokio::join!`s the gogdl-lib future with its progress reporter, and nothing can stop it. When Dart cancels its subscription, only the sink goes away: `let _ = sink.add(...)` swallows the error, and the Rust job keeps downloading or hashing until it finishes. `guardBridgeStream`'s `onCancel` cancels the Dart subscription only. | Phases 3–6 |
| D2 | gogdl_flutter | **A terminal `Cancelled` variant** on `DownloadGameProgress`, `VerifyDownloadProgress` and `RepairGameProgress`. On cancel, emit it and return `Ok(())`, not an error. | `GogError` is opaque, and Lumen only gets its `message()` string. A cancel reported as an error could only be recognized by string matching. An in-band event also keeps `guardBridgeStream`'s error path for real failures, and the exhaustive `switch`es in `DownloadsNotifier` break at compile time until the new variant is handled. | Phases 3–6 |
| D3 | gogdl_flutter | **`get_install_size(game_id, build_name, selected_products) -> InstallSize { download_bytes, disk_bytes }`.** It's built from `get_product_bundles`, the same bundles `download_game` uses. `download_bytes` is the sum of the chunks' `compressed_size` (the `Started.total_bytes` figure) and `disk_bytes` the sum of their `size`. | No size is known before a download starts. `DownloadGameProgress.Started` carries the compressed total only after the job is already running. The app-owned model is `lib/models/install_size.dart`, per CLAUDE.md's rule that bridge data types get adapted. | Phase 9 |
| D4 | gogdl-lib | **A public free-space query**: `GogDl::get_free_space(path) -> Result<u64, GogDlError>`, a thin wrapper over `PathResolver::get_free_space`. `fs` is a private module today. | Lumen's pre-check should compute free space exactly the way the lib's own pre-flight check in `Downloader::download`/`repair` does. Otherwise Lumen could say "fits" and the lib then fail with `NotEnoughFreeSpace`, or the other way round. | Phase 9 |
| D5 | gogdl-lib | **Fix `PathResolver::get_free_space`'s mount lookup** to pick the *longest* matching mount point, not the first. It currently does `disks.list().iter().find(\|d\| base.starts_with(d.mount_point()))`, and `/` is a prefix of every path. | The lib's own check reads the root filesystem's free space for an install on a separate mount. **Confirmed in Phase 0:** `sysinfo` 0.39.6 keeps `/proc/mounts` order and `/` comes first, so a path on `/media/gamedisk` got `/`'s 325.6 GB instead of the disk's real 16.8 GB (`/media/st` likewise). Phase 9 would show the wrong number too. | Phase 9 (and the lib's own check) |

Accept a cancel token and await the `spawn_blocking` extraction before returning. | A failed Proton download leaves a half-extracted directory under `<lumenDataDir>/proton`, and Lumen can't know its name (the tarball root, not the tag). This matters for Proton cancel (out of scope), and it's a leak today on any failure. | — (GAPS note) |
| D7 | gogdl_flutter | *(Recommended after Phase 0.)* `GogError.kind()`, a sync enum (`notEnoughFreeSpace`, `couldNotResolveFreeSpace`, `fileAllocation`, `network`, `auth`, `other`). | This would let Phase 8's error text say "Not enough disk space" in Lumen's own words, not gogdl-lib's `Display` text. Phase 0 shows the `Display` text does not read well: `gogErrorText` gives `Download error: Not enough free space`, `Download error: File allocation error`, `Download error: Client error: Max retires reached` (typo, fix it in gogdl-lib) and `Download error: Client error: Network error: error sending request for url (...)`. | — |

**What doesn't need a dependency change**, and why:
- **Resume (B).** `GogDl::repair_game`'s doc comment says it is *"the resume path. Since this crate
  has no separate pause/resume mechanism, calling this on a partially-downloaded install … is how
  you continue it without re-transferring already-correct data."* Lumen already wraps it as
  `GogBackend.repairDownload`.
- **Cancelling games' jobs in gogdl-lib itself.** `downloader.rs` uses `buffer_unordered` streams
  and no `tokio::spawn`, so dropping the future from the bridge's `select!` really stops the
  transfer. Phase 0 double-checks this. A chunk write cut off halfway leaves a bad chunk, which is
  harmless because resume goes through `repair_game`, and that verifies checksums.
- **Uninstall (D), Proton removal (F), and the Downloads page (C).** All pure Lumen. `ActivityTask`
  already has an `error` field (added after GAPS was written), so "real error text" is mostly a UI
  audit.

**Release order for the deps:** gogdl-lib first (D4, D5), tagged as that repo's next version
(`v1.0.12` if it keeps bumping the patch for features, as with `v1.0.11`). Then gogdl_flutter
(D1–D3) pins that tag and gets its own next tag. Its tags currently come from `feat/cloud-saves`,
not `main`, so decide there whether to merge that branch first. Lumen then pins the bridge tag in
Phase 3.

## Ordering rationale

- The investigation (Phase 0) comes first. Several phases depend on facts not in either repo: what
  FRB actually does to a running Rust job when the Dart side cancels, what a killed download leaves
  on disk, how long `repair_game` takes to resume a big partial install, and whether D5's mount bug
  reproduces.
- Proton removal (Phase 1) has no dependency and is small. It also introduces the guarded
  directory-deletion helper that Phases 5 and 7 reuse. It can be done while Phase 2 is still in
  progress.
- The dependency work (Phase 2) and the Lumen plumbing for it (Phase 3) come before anything that
  cancels. Phase 3 only teaches the interface, the fake and `GogState` about tokens and the new
  variants, so later phases have one small seam to test against.
- Cancel for verification and repair (Phase 4) comes before downloads. Those jobs have no
  persisted state, so the cancel mechanics (stale-commit guard, a new `TaskStatus`) can be settled
  without also changing the games schema.
- Pause and resume (Phase 5) come before recovery after an app exit (Phase 6). Once a paused
  download is a persisted, resumable state, an interrupted one is just a paused one found at
  startup.
- Uninstall (Phase 7) comes after cancel, because uninstalling a game with a running job has to
  cancel that job first. It reuses Phase 1's deletion helper.
- The Downloads page cleanup (Phase 8) comes after every new status (cancelled, paused) exists, so
  dismiss, clear and Retry are designed once, for all of them.
- The disk space check (Phase 9) comes last. It only touches the install flow, and it's the one
  item that could slip to a `v1.3.1` patch if D3–D5 stall, without holding the rest back.

## Phase 5 — Pause, resume and cancel downloads

Files: `lib/state/games_state.dart` (schema v2), `lib/state/downloads_state.dart`,
`lib/components/game_action_buttons.dart`, `lib/screens/home/pages/downloads_page.dart`, tests.

A download has files on disk, so it needs two actions. **Pause** stops the job and keeps the files
for a later resume. **Cancel** stops it and discards them. Per Phase 0, a resume must use
`repairDownload`, never `downloadGame`, because preallocated files would pass `download_game`'s size
check without their data.

- [ ] Add `GameStatus.paused`: files are partially on disk and resumable. Grep every use of
  `GameStatus` and handle it. The library filters show it with "Installing", and
  `GameActionButtons` shows Resume and Cancel in place of Install.
- [ ] **Decide where a paused download's path lives** (your call; recommended first, informed by
  Phase 0's `installPath` audit):
  - (a) **Recommended, and backed by Phase 0's audit** (about 10 readers assume a path means installed: `launch_state`, `launch_resolver`, `game_action_buttons`, `builds_tab`, `saves_state`, `game_settings_tab`, `overview_tab`, ...). A new `GameConfig.pendingInstallPath`, set when a download starts and
    cleared on completion (when `markInstalled` moves it to `installPath`), on cancel, and on
    uninstall. None of the existing `installPath` readers need to learn that "a path doesn't
    always mean installed".
  - (b) Set `installPath` at download start and gate every reader on `status == downloaded`. It's
    one field fewer, but every reader Phase 0 found becomes a potential bug.
- [ ] Schema: bump `gamesSchemaVersion` to 2 and append a `_migrations` step (per CLAUDE.md). The
  step rewrites a v1 `status: downloading` to `notInstalled`, since a v1 entry has no path to
  resume from, which is today's decode-time coercion moved into the migration. A migration test
  loads a v1 blob and a bare pre-envelope blob.
- [ ] `DownloadsNotifier.pause(gameId)` (download tasks only): cancel via `JobCancel`, and on
  `Cancelled`, commit `TaskStatus.paused` (new) and set `GameStatus.paused`.
  `resumeDownload(gameId)`: start a repair job with the saved path, build and products. The card
  still reads as a download ("Resuming — verifying downloaded files…", then the usual download

- [ ] `cancelDownload(gameId, {required bool deleteFiles})`: if the job is running, cancel it and

- [ ] **Decide what "delete files" deletes** (your call): the whole chosen directory (recommended:

- [ ] UI: Pause and Cancel on a running download card and in `GameActionButtons`; Resume and Cancel

- [ ] Tests: pause → `paused`, the game is `paused`, `pendingInstallPath` is persisted; resume calls

**Done when:** a download can be paused, resumed (and finishes installed) and cancelled with or
without its files, all within one app session.

## Phase 9 — Disk space check before install

Files: `lib/components/game_action_buttons.dart` (the Install flow after `DirPicker.pick()`),
`lib/common/format.dart` if a helper is needed, tests.

- [ ] Free-space figures are only trustworthy for separate mounts once D5 is in (see Phase 0).
- [ ] After a directory is picked, call `getInstallSize(gameId, build, products)` and
  `getFreeSpace(dir)` in parallel, with a busy state on the Install button while they run
  (`get_product_bundles` fetches manifests, which can take a few seconds on big games).
- [ ] Show a confirm dialog: "Download 12.3 GB · Needs 25.1 GB on disk · 80.4 GB free on `<mount>`".
  If `disk_bytes > free`, block the install with "Not enough space: needs X, only Y free" and offer
  "Choose another folder".
- [ ] **Decide the margin** (your call): compare `disk_bytes` against free space exactly (the lib's
  own check does), or require headroom (e.g. +5%, to cover filesystem overhead and a shader cache).
  Recommended: exact, to match the lib, with a warning (not a block) when less than 5% would
  remain.
- [ ] If either call fails, don't block. Show "Couldn't determine the download size" in the dialog
  and let the user continue: the lib's own pre-flight check still stops a download that really
  doesn't fit.
- [ ] Import doesn't get this check (nothing is downloaded). Resume and Retry don't either: the
  repair pre-flight already checks only the missing files, and a partial install would make the
  full-size figure misleading.
- [ ] Tests (widget, with the fake's `installSize`/`freeSpace`): the dialog shows the sizes; an
  insufficient-space case blocks and doesn't call `downloadGame`; a failed size lookup still allows
  the install.

**Done when:** installing to a folder without enough room is refused before any download starts,
with the numbers shown.
