# v1.2.0 — Launching and Proton work plan

The work plan for the `v1.2.0` entry in [ROADMAP.md](ROADMAP.md) and its `v1.2.1`–`v1.2.5` follow-up
patches: how a game gets resolved, spawned, logged and stopped, and how much Lumen trusts the Proton
install it spawns it with. Each phase below should fit in one short session and end with a green
`fvm flutter analyze --fatal-infos` and `fvm flutter test`, plus one commit. The `v1.2.0` tag is cut
only at the end of Phase 7, so `main` keeps shipping as `1.1.6` until then. The patches after that
get one tag each, per the ROADMAP versioning rules.

Tick each checkbox as it's done. If a phase turns out bigger than one session, split it here before
starting, not halfway through.

| B | Resolve executables from `goggame-<id>.info` `playTasks`, keeping the scan as a fallback | §3 P1 | 2, 3 |
| C | Move the executable scan off the UI isolate | §3 P1 | 2, 3 |
| D | Re-scan or prompt when the stored executable is missing | §3 P1 | 4 |

Then the patches, one tag each (Phases P1–P5):

| Tag | Item | GAPS |
|---|---|---|
| `v1.2.1` | Check `wineboot`'s exit code | §3 P2 |
| `v1.2.2` | Validate the Proton binary and wrapper before spawning | §3 P2 |
| `v1.2.3` | Stop treating every non-zero exit as a failure | §3 P2 |
| `v1.2.4` | Remove the `[DIAG]` prints | §3 P2 |
| `v1.2.5` | Validate installed Proton versions against disk on load | §3 P2 |

**Out of scope for Phases 1–6:** everything in the patch list. Phases 5 and 6 rewrite a lot of
`LaunchNotifier.launchGame`, so the `[DIAG]` prints, the unchecked `wineboot` result and the
non-zero-exit-is-failure rule will all be right in front of you. Keep the existing ones where the
code they sit in survives (don't add new `[DIAG]` lines), and note anything you find under the
matching patch below instead of fixing it early. The one deliberate exception is in Phase 6: a game
the *user* stopped must never be reported as failed, whatever its exit code (see there).

Also out of scope (note in GAPS if it comes up): prefix tools, playtime tracking, `.desktop`
shortcuts (all `v1.6.0`), and what happens to a running game when Lumen itself exits.

## Ordering rationale

- The investigation (Phase 0) comes first because three later phases depend on facts about real
  installs that aren't in the repo: the `.info` file shape, the Proton-GE directory layout
  (`wineserver`'s location, for Stop), and what the process tree looks like under `proton run`.
- The tokenizer (Phase 1) goes before `playTasks` because a playTask's `arguments` is a single string
  that has to be split the same way the user's launch args are. It's also the only pure,
  dependency-free item, so it's a cheap warm-up.
- Resolution is split into the pure part (Phase 2: parse `.info`, run the scan in an isolate, both
  unit-tested) and the wiring (Phase 3: one resolver shared by Play and the Settings tab). The stale
  executable case (Phase 4) builds on that resolver instead of adding a third code path.
- Logs (Phase 5) go before Stop (Phase 6). Both restructure how `LaunchNotifier` owns the spawned
  `Process`, and logs are the simpler of the two. Having per-game logs also makes Stop's
  process-tree behavior much easier to debug.
- The patches come after the tag because they're each small and independent, and ROADMAP already
  fixes their order. Where a phase makes one of them easier (logs make `v1.2.1`'s error message
  useful; Phase 6's "stopped isn't failed" rule is a subset of `v1.2.3`), the patch section says so.

## Phase 1 — Shell-style tokenizing

Files: new `lib/common/shell_words.dart`, `lib/screens/home/pages/library/game_settings_tab.dart`.

Today `_persistLaunchWrapper`/`_persistLaunchArgs` (`game_settings_tab.dart:104,113`) split on
`\s+`, and the controllers are seeded with `.join(' ')`, so `--config "My Documents/x.ini"` can't be
expressed and wouldn't round-trip if it could.

- [x] Add `List<String> splitShellWords(String input)`, a POSIX-ish subset:
  - whitespace separates words; runs of whitespace collapse,
  - `'…'` is fully literal,
  - `"…"` is literal except that `\"` and `\\` escape,
  - a `\` outside quotes escapes the next character,
  - quotes join with adjacent text (`--dir="a b"` → one word `--dir=a b`),
  - `""` gives an empty word (it is not dropped),
  - **no** variable expansion, globbing, `~` or command substitution. Say so in the doc comment.
  - Throw a `FormatException` on an unterminated quote or a trailing lone `\`.
- [x] Add `String joinShellWords(List<String> words)`, the inverse: quote only the words that need it
  (whitespace, quotes, `\`, empty), preferring single quotes. `splitShellWords(joinShellWords(x)) ==
  x` must hold for every `x`.
- [x] `test/common/shell_words_test.dart`: the cases above, the error cases, and a round-trip test
  over a handful of awkward lists (spaces, both quote kinds, backslashes, empty words, unicode).
- [x] `GameSettingsTab`: seed both controllers with `joinShellWords`, and persist with
  `splitShellWords`. On a `FormatException`, show it inline as the field's `errorText` and **don't**
  persist, so the last valid value stays saved. Clear the error on the next valid edit.
- [x] Make `_resolvedCommand`'s preview use `joinShellWords` too, so what it shows is what will run.
- [x] Storage is unchanged (`List<String>` in `GameConfig`), so no `gamesSchemaVersion` bump. Existing
  configs load as-is. The only visible change is that a stored word containing a space now shows
  quoted in the field.

**Done when:** `"a b" c` in the launch-args field persists as `["a b", "c"]`, shows back as
`'a b' c`, and an unterminated quote shows an error without losing the saved args.

## Phase 2 — `playTasks` parsing and an off-isolate scan (pure units)

Files: new `lib/common/goggame_info.dart`, `lib/common/executable_finder.dart`, their tests. No UI
changes yet.

- [x] Add a small app-owned `LaunchTarget` model (`executable` relative to the install root,
  `workingDir` relative to it or null for "exe's parent", `arguments` as `List<String>`, plus a
  `source` enum: `userOverride` / `gogMetadata` / `scan`). Put it in `lib/models/` next to the other
  app-owned models, with `==`/`hashCode`.
- [x] `goggame_info.dart`: `Future<LaunchTarget?> readPrimaryPlayTask(String installPath, int
  gameId)`:
  - reads exactly `<installPath>/goggame-<gameId>.info` (always at the install root, per Phase 0)
    and returns null if it's missing or unparseable. Never glob for `goggame-*.info`: the install
    root also holds each DLC's `.info` (with `playTasks: []`), and Phase 0 found other games'
    `.info` files sitting in shared or reused install dirs. Strip a UTF-8 BOM before decoding
    (none seen, but it's free). Never throw into the launch flow; log via `logGogError`.
  - **Decide launcher vs. game** (your call; recommended first). Phase 0 found `isPrimary` is very
    often a `category: launcher` task (`REDprelauncher.exe`, `launcher.exe`, `dowser.exe`,
    `SWB2Launcher.exe`), with the real game as a `category: game`, `isHidden: true` task:
    - (a) **Recommended.** Pick the primary task if it's `category: game`; otherwise the first
      `category: game` `FileTask` (hidden or not); otherwise the primary (the launcher). Launchers
      make `proton run` return while the game keeps running (see Phase 0), which breaks "exited",
      logs and Stop, and the stored overrides on the dev machine already point past them
      (`bin/x64/Cyberpunk2077.exe`, `bin/x64_dx12/witcher3.exe`).
    - (b) Always the primary, like Galaxy/Heroic. Faithful, but lands on the launcher for most
      big titles.
    - **Decided: (a).** Selection runs over the tasks whose exe exists on disk, so a missing hidden
      game exe falls back to the launcher primary, and null only when no listed exe exists.
  - ignores `URLTask`s, `tool`/`document`/`other` entries, and any `FileTask` whose path doesn't end
    in `.exe` (case-insensitive). Some tasks have no `category` at all (The Witcher's "[Safe
    Mode]"); treat a missing category as "not game" for primary selection, but list it.
  - `path` and `workingDir` mix `\` and `/`, and can contain `//` (`System//witcher.exe`):
    normalize `\` to `/` and collapse empty segments (`package:path`'s `normalize`; `path` is now a
    direct dependency). A path or `workingDir` that is absolute or escapes the root (`..`) drops
    the task; an empty `workingDir` counts as absent. Both are
    relative to the install root (which is also the `.info` file's own directory).
  - tokenizes `arguments` with Phase 1's `splitShellWords`. Observed values are
    `-dontForceMinReqs` and `--launcher-fallback="DirectX 11"` (Windows-style double quotes
    joined to text, which Phase 1 handles). A Windows path with `\` outside quotes would be eaten
    as an escape; none was seen, so just note it in a comment. If splitting throws, fall back to a
    whitespace split rather than dropping the task.
  - returns null if the resolved exe doesn't exist on disk, so a stale `.info` falls through to the
    scan. Tasks pointing at missing files are real (Star Wars Battlefront II's
    `language_setup.exe`).
  - ignores `languages`, `osBitness`, `compatibilityFlags`, `runAsAdmin`, `isHidden` (beyond (a)),
    `icon` and `additionalPaths`.
- [x] Also expose `listPlayTasks(...)` returning every `.exe` `FileTask` with a `name` that exists
  on disk, launchers included (so a user who wants the launcher can pick it). This is optional for
  the UI in this release, but the Settings tab picker can show "GOG: <name>" entries above the scan
  results if it's cheap.
- [x] `executable_finder.dart`: keep `findExecutables` as the synchronous pure function (its
  existing tests stay), and add `Future<List<String>> findExecutablesAsync(String installPath) =>
  Isolate.run(() => findExecutables(installPath))`. `findExecutables` is top-level and captures only
  a `String`, so it's isolate-safe. Add a comment saying so, so nobody later closes over a `ref`.
- [x] Leave the skip-lists alone: the known false negatives stay characterized (the existing
  "known false negatives" group). The scan is the fallback now, and loosening it would just widen
  the picker. Update that group's comment to say playTasks supersedes it for games that ship
  `.info`.
- [x] `test/common/goggame_info_test.dart`: build temp installs from the real `.info` samples
  collected in Phase 0 (anonymize if needed) covering primary selection, `isPrimary` missing,
  a launcher primary with a hidden game task (Cyberpunk 2077 / The Witcher 3 shape), two game tasks
  (The Witcher 3: first one wins), `URLTask`-only, backslash and `//` paths, `workingDir`
  present/absent, a task with no `category`, quoted arguments, a DLC `.info` with `playTasks: []`,
  another product's `.info` in the same dir being ignored, a missing exe → null, a corrupt JSON →
  null, and no `.info` file → null.
- [x] One test that `findExecutablesAsync` returns the same list as `findExecutables` for the
  existing fixture tree.

**Done when:** both units are tested, `grep -rn "findExecutables(" lib` still shows only the two

## Phase 6 — Stop a running game

Files: `lib/state/launch_state.dart`, `game_action_buttons.dart`, `launch_state_test.dart`.

`LaunchNotifier` keeps no handle today: the `Process` is only reachable inside `launchGame`'s
closure.

- [x] Keep a private `Map<int, _LiveLaunch>` in `LaunchNotifier` (the `Process`, the Proton path,
  the prefix path, a `stopRequested` flag). **Not** in `RunningGame`/`LaunchState`: those stay
  immutable value snapshots, and a `Process` in state would break that and every `==`. Remove the
  entry when the exit is handled. **Added:** `_LiveLaunch` also holds the launch's log and its
  latest `RunningGame` (`live.game`). Once the process has started, every commit goes through
  `live.game`, so `stopGame`'s `stopping` commit and the exit commit share one identity for
  `_commit`'s stale check.
- [x] Add `LaunchStatus.stopping`. `isActive` stays true for it, so Play can't relaunch mid-stop.
  Grep for every `switch`/`==` on `LaunchStatus` in `lib/` and handle the new value.
- [x] `Future<void> stopGame(int gameId)`: a no-op unless `running`. Commit `stopping`, then:
  1. run the release's `<protonPath>/files/bin/wineserver -k` (Phase 0: that's the only layout in
     current GE; its `proton` script only mentions `dist/` to delete it, so no fallback), with
     `WINEPREFIX=<prefixPath>/pfx` plus the same compat env. This takes down every Wine process in
     that prefix, and `proton run` exits on its own. It's the only step that can reach the game:
     Windows processes are reparented to init in their own session, so they're never descendants
     of the spawned process.
  2. If the spawned process hasn't exited within a grace period (~5 s), `SIGTERM` it. That covers a
     wrapper like `gamescope` that outlives its child. After another ~3 s, `SIGKILL`. Signal the
     pid only, never `-pgid`: Phase 0 found `Process.start` children share Lumen's own process
     group. A wrapper's own children may be orphaned by this; real `gamescope` handles `SIGTERM`
     itself.
  3. If `wineserver` itself is missing or fails, log it to the game log and go straight to step 2.
     **Done:** a non-zero rc also counts as failing, and "straight to step 2" means SIGTERM with no
     grace wait. A stop still in flight after the game exited writes nothing more (its log is closed).
  Adjust these steps to whatever Phase 0 actually observed.
- [x] `WINEPREFIX` here is a deliberate exception to "the only env vars the tool injects are the two
  `STEAM_COMPAT_*` ones": it goes to `wineserver`, never to the game. Update CLAUDE.md's
  Proton/launching section to say exactly that.
- [x] Exit handling: when `stopRequested` is set, the exit is `exited` (not `failed`) whatever the
  code. This is the one piece of `v1.2.3` pulled forward, because otherwise every Stop pops the
  failure snackbar. General non-zero handling stays as-is until `v1.2.3`. Write "Stopped by user"
  in the log footer.
- [x] UI: while running, the "Running…" button becomes "Stop" (a destructive-styled secondary button;
  no confirmation dialog, since stopping a game is what the button says). While stopping, a
  disabled "Stopping…". **Done:** `PrimaryButton.icon` with `glowing: false` and
  `foreground: AppColors.error`. `launching` now reads a disabled "Launching…" instead of
  "Running…", since it can't be stopped yet.
- [x] Tests, using a fake proton script that `sleep`s until killed plus a fake `wineserver` script in
  the release layout that logs its argv and `$WINEPREFIX` and kills the sleeping script's PID
  (written to a file on start):
  - `stopGame` runs `wineserver -k` with `WINEPREFIX=<prefix>/pfx`, and the game ends `exited`, not
    `failed`, even though the killed script exits non-zero (real `proton run` returned 0 after
    `wineserver -k` in Phase 0, but don't rely on that),
  - with a `wineserver` that does nothing, the process is SIGTERMed after the grace period. Make
    the grace periods injectable (a `@visibleForTesting` field or constructor arg) so the test
    doesn't wait 5 s,

### P1 — `v1.2.1`: check `wineboot`'s exit code

`launch_state.dart:147` awaits `Process.run(... 'wineboot')` and ignores the result.

- [ ] A non-zero exit fails the launch: `failed`, `"Prefix initialization failed (exit N) — see the
  log"`. The wineboot output is already in the log from Phase 5, so the snackbar's "Open log" action
  is the useful part.
- [ ] **Decide what happens to a half-created `pfx`** (your call): today "is initialized" means
  "`pfx` exists", so a failed wineboot that still created `pfx` gets skipped next time and the game
  runs in a broken prefix. Recommended: on failure, delete `<prefix>/pfx` (it's Lumen-owned and was
  just created by this very call), so the next launch retries init. The alternative is an explicit
  marker file written only on success. That's more robust, but existing initialized prefixes don't
  have it, so it needs an "assume initialized if `pfx/drive_c` exists" migration rule.
- [ ] Tests: a fake proton script whose `wineboot` exits 1 (and creates `pfx`) → `failed` with that
  message, the game is never spawned, and the next launch runs wineboot again.

### P2 — `v1.2.2`: validate before spawning

- [ ] Before anything runs (wineboot included), check that `$protonPath/proton` exists and is
  executable (`FileStat` mode bits). Otherwise: `"Proton-GE <tag> is missing its proton script at
  <path> — reinstall it in Settings"`.
- [ ] If there's a wrapper, check its first token: a path (contains `/`) must exist and be
  executable; a bare name must be found on `PATH` (walk `Platform.environment['PATH']`). Otherwise:

- [ ] Both failures happen **before** `pfx` is created and before a log is rotated, so a

- [ ] Tests: update the existing "missing proton binary → failed with an error" test to assert the

### P3 — `v1.2.3`: non-zero exits aren't automatically failures

`launch_state.dart:178` maps any non-zero code to `failed`, and since v1.1.0 Phase 6 the failure
snackbar actually fires, so this is visible on every normal quit of some games.

- [ ] **Decide the policy** (your call; recommended first):
  - (a) **Recommended.** A spawned game always ends `exited`, with `exitCode` kept. `failed` is
    reserved for Lumen-side failures (spawn errors, validation, wineboot). One exception: a non-zero

    (code N)"`, since that's almost always a real crash-on-start. Use Phase 0's observed exit codes
    to sanity-check the window.
  - (b) Always `exited`; never infer failure from the code. Simpler, but a crash-on-launch then looks
    like nothing happened.
  - (c) A per-game "treat non-zero exit as error" toggle. Probably overkill.
- [ ] Update the "non-zero exit code → failed" test to the new rule; add "non-zero after the window
  → exited", and make the window injectable so the test doesn't wait.

### Phase 0 findings

**`goggame-<id>.info`** (9 installs, 21 files: The Witcher EE, Cyberpunk 2077 + Phantom Liberty +
REDmod, The Witcher 3 GOTY, Metal Gear Solid, Alien: Isolation + 7 DLC, Brigador, Hellpoint, Star
Wars Battlefront II, Prison Architect):

- Always at the install root, never nested. Named after the product id, so the base game's file
  matches Lumen's `gameId`. Each DLC has its own `goggame-<dlcId>.info` next to it with
  `playTasks: []` (and `rootGameId` = the base game).
- Other products' `.info` files can share the dir: a Witcher EE `.info` sits in the Cyberpunk dir,
  and Prison Architect and Alien: Isolation share an install path in the dev prefs. So read exactly
  `goggame-<gameId>.info`, never glob.
- Plain UTF-8 JSON, no BOM. `buildId` can be missing (MGS).
- `category` values: `game`, `launcher`, `tool`, `document`, `other`, and sometimes none at all
  (The Witcher's "[Safe Mode]" task). `type`: `FileTask` / `URLTask` (URLTasks have `link`, no
  `path`). Extra fields: `isHidden`, `languages`, `osBitness`, `compatibilityFlags`, `runAsAdmin`,
  `icon`, `additionalPaths`.
- **`isPrimary` is usually a launcher** on bigger titles: `REDprelauncher.exe` (CP2077, W3),
  `launcher.exe` (Witcher EE), `Launcher/dowser.exe` (Prison Architect), `SWB2Launcher.exe` (SWBF2).
  The real game is then a `category: game`, `isHidden: true` task. Simple games (MGS, Alien,
  Brigador, Hellpoint) have a primary `category: game` task. W3 has two game tasks (DX12, then
  DX11), MGS has two (game, VR Missions).
- `path`/`workingDir` mix `\` (`System\\witcher.exe`, `bin\\x64\\Cyberpunk2077.exe`) and `/`
  (`bin/x64_dx12/witcher3.exe`), and one has `System//witcher.exe`. All resolve against the install
  root (the `.info` file's own dir too, so there's no way to tell the two apart). `workingDir` is
  present on some game tasks (`System`, `bin/x64_dx12`, `GameData`), absent on others, including
  CP2077's `bin\\x64\\Cyberpunk2077.exe`.
- `arguments` seen: `-dontForceMinReqs`, `--launcher-fallback="DirectX 11"` (Windows-style quotes
  joined to text).
- Some `FileTask`s point at missing files: SWBF2's `language_setup.exe`, and The Witcher's
  `Manual.pdf`/`Readme.rtf`.

**Proton-GE layout** (GE-Proton11-5, 11-6, 11-7): `wineserver` is at `files/bin/wineserver` in all
three; no `dist/` anywhere. The `proton` script only mentions `dist/` in `cleanup_legacy_dist`, which
deletes it. (`files/bin-arm64/` is used on aarch64 only.)

**Process tree and `wineserver -k`** (scratch prefix, synthetic exes, since that needs no human to
quit a game):

- `proton run <exe>` → `python3 proton` → Proton's `steam.exe` shim runs the target. The Windows
  processes, the game exe included, are **not** its descendants: they're reparented to init (ppid 1)
  in their own session/pgid, alongside `wineserver`, `services.exe`, `explorer.exe`, etc.
  Signalling the spawned process or its group can't reach the game.
- `WINEPREFIX=<prefix>/pfx files/bin/wineserver -k` returns in ~50 ms with rc 0 and kills every Wine
  process in the prefix. `proton run` then returns **rc 0**.
- Launcher-style exe (`cmd /c start ping.exe …`): `proton run` returned rc 0 after 2 s while the
  spawned child kept running. So **yes, "exited" can mean "Proton returned"**, not "game closed".
  Not fixed in this release, per the plan. It matters for any launcher-primary playTask (see Phase 2
  (a)).
- `wineserver` lingers a few seconds after `proton run` returns, even with nothing running (normal
  Wine persistence).
- Wrapper: `gamescope` isn't installed on the dev machine, so a non-`exec` shell wrapper stood in.
  After `wineserver -k`, `proton` returned but the wrapper kept running. `SIGTERM` to its pid ended
  it (rc 143), but orphaned the wrapper's own child. Dart's `Process.start` children share Lumen's
  process group, so a `-pgid` kill would hit Lumen itself. Phase 6 signals the pid only.
- Fresh-prefix `proton run wineboot` took ~2 s with rc 0 (GE copies `default_pfx`). Relevant to
  `v1.2.1`.

**Real games** (launched exactly like `launchGame`, GE-Proton11-7, each quit normally from the
in-game menu). The probe snapshotted at +5/10/20/30 s, so return times are bounded by snapshots:

| Game | Target | `proton run` returned | What kept running | rc |
|---|---|---|---|---|
| The Witcher 3 | `REDprelauncher.exe` (the `isPrimary` task) | within 5 s | `REDlauncher.exe` + `QtWebEngineProcess.exe`, then `bin/x64_dx12/witcher3.exe` (+10 s to +20 s); the launcher outlived the game by ~10 s | 0 |
| Hellpoint | `Hellpoint.exe` | when the game quit (20–30 s) | nothing (`Hellpoint.exe` + `UnityCrashHandler64.exe` ended with it) | 0 |

- **Confirmed on a real game:** with a launcher target, `proton run` returns within seconds while
  the launcher and the game run on. Lumen would show "exited" for the whole session. That's the main
  argument for Phase 2 (a).
- A direct game exe (Hellpoint) keeps `proton run` alive exactly as long as the game, with the game
  exe outside its process tree (ppid 1), as in the synthetic tests.
- **Exit codes:** every normal quit gave rc 0 (for W3 that's the launcher's rc, not the game's). No
  non-zero normal quit was observed, so `v1.2.3` has no real-world counterexample yet. Its
  immediate-exit window (option (a)) must also allow for a "successful" rc 0 return within seconds
  from launchers.
- `gamescope` couldn't be tested (not installed). The shell-wrapper stand-in above covers the
  wrapper-outlives-proton case.
