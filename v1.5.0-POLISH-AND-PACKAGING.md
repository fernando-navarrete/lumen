# v1.5.0 — UI polish and packaging work plan

The work plan for the `v1.5.0` entry in [ROADMAP.md](ROADMAP.md) and its `v1.5.1`–`v1.5.2`
follow-up patches: a login screen that doesn't flash, guess or overflow, a proper window (minimum
size, icon), one responsive breakpoint helper for the detail tabs, keyboard focus and semantics for
`ClickableContainer`, adopting the bridge's breaking `v1.5.0` cleanup, and an AppImage (and possibly
a Flatpak) built and published by a release pipeline. Each phase below should fit in one short
session and end with a green `fvm flutter analyze --fatal-infos` and `fvm flutter test`, plus one
commit. Phase 6 is the exception: it happens in the dependency repos, not here.

Tick each checkbox as it's done. If a phase turns out bigger than one session, split it here before
starting, not halfway through.

## Branching

`main` is protected (see [devlog/ci-cd-merge-requests.md](devlog/ci-cd-merge-requests.md)): nobody
pushes to it, and every change lands through a merge request. This release has no long-lived branch.
Each group of phases gets a short-lived branch and one MR, merged semi-linearly, with the source
branch deleted on merge.

- **MR grouping** (proposal, kept sparse):
  - `feat/v1.5.0-polish`: Phases 1–5, everything that needs no dependency change. It can merge while
    Phase 6 is still in progress in the dependency repos.
  - `feat/v1.5.0-bridge`: Phase 7 alone. The bridge's `v1.5.0` is breaking, so the pin and every
    migration it forces land together, or `main` doesn't build.
  - `release/v1.5.0`: Phases 8–10 (packaging, the release pipeline, the release itself).
  Phases 8–9 merged on their own, so Phase 10 used a separate short-lived `release/v1.5.0-final`.
  Each MR leaves `main` releasable. `pubspec.yaml` stays at `1.4.3` until Phase 10.
- Each phase is still one commit on the MR's branch, so the merge commit shows the phases underneath.
  Use squash only for an MR whose branch has red or revert commits.
- The MR pipeline runs lint, test and scan on the branch. Still run `analyze` and `test` locally
  every phase. Phase 9 adds a packaging job to MR pipelines so the AppImage build is proven before
  any tag depends on it.
- Phase 10 tags `v1.5.0` on `main`'s merge commit after its MR merges. That tag pipeline is the
  release pipeline's first real run.
- The patches (P1–P2) are one MR each, or one MR for both with a tag per merge commit. Tag on
  `main`'s merge commit after the merge.
- A `v1.4.x` hotfix is the only case that uses the cherry-pick path described under "Decisions" in
  devlog/ci-cd-merge-requests.md.
- While Phase 6 is in progress, `feat/v1.5.0-bridge` may point `gogdl_flutter` at a branch `ref`. It
  must be back on a **tag** before Phase 7's commit. The lockfile's `resolved-ref` is what CI builds
  against, and `tool/check_bridge_pin.sh` fails `lint` on anything that isn't a `vX.Y.Z` tag. If the
  bridge's Rust pin changes, bump the CI image tag in `.gitlab-ci.yml` in the same commit.

update that row in the bridge repo too.

## Ordering rationale

- The investigation (Phase 0) comes first. Packaging hinges on facts that aren't in any repo: whether
  a Flatpak can run Proton and see user-chosen install folders at all, which glibc the CI image's
  build needs, what the AppImage runtime leaks into child processes, and what `loginWithCode`
  actually returns for a bad, reused and expired code.
- Window, breakpoints and `ClickableContainer` (Phases 1–3) are small and independent, so they go
  first and start the polish MR while Phase 6 runs. The window phase also produces the icon and
  `.desktop` file Phase 8 packages.
- The breakpoint helper (Phase 2) goes before the login screen (Phase 5), which reuses it for its
  small-window layout.
- The deprecated getters (Phase 4) go before Phase 7, so the breaking pin is a mechanical migration
  and not also a behavior change in the hero banners and the Proton dialog.
- The login screen (Phase 5) goes before the dependency work lands: everything except the new error
  kinds is Lumen-only. Phase 7 then wires the kinds into an error path that's already structured for
  them.
- The dependency work (Phase 6) and adopting it (Phase 7) come before packaging, so the first
  released AppImage carries the bridge `v1.5.0` it will be supported against, not one about to break.
- Packaging (Phase 8) before the release pipeline (Phase 9): the pipeline only automates a script
  that already works locally.
- Phase 10 releases. If Flatpak stalls (Phase 0's most likely outcome), ship the AppImage alone and
  move Flatpak to GAPS, without holding the rest back.
