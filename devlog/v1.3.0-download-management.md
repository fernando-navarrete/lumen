# Devlog — v1.3.0 Download management

Cancel, pause and resume for downloads, cancel for verification and repair, uninstall, Downloads
page actions, a disk space check before install, and Proton version removal — the `v1.3.0` ROADMAP
entry. Built on its own branch, `release/v1.3.0`, as eleven phases (0–10) over 2026-09-24 to 26,
with Phase 2 done in the dependency repos. Kept here for the decisions and pitfalls that aren't
obvious from the diff. Ended at 357 passing tests, `flutter analyze --fatal-infos` clean, and a
green CI run on `v1.3.0-rc.1`.

## Phase 0 — Investigation

**Does a Dart-side cancel stop the Rust job?** No. Cancelling the stream subscription 8 seconds
after the first progress event left the install dir growing (~1 MB/s) more than four minutes later.
Only the sink goes away; the job runs to the end. That is what motivated a real cancel token in the
bridge (D1). It was later superseded: with `gogdl_flutter` `v1.3.0`, dropping the subscription
stops the job within ~150 ms.

**What a killed download leaves behind.** Sparse, preallocated files (546,197,047 bytes apparent,
~209 MB on disk). `download_game`'s size check would call those files done, so resume must always go
through `repair_game`, never `download_game`. A repair on that dir re-downloaded only the missing
part and finished within about a minute, but the game was small and the timings weren't captured.
**Big-game resume timing was never measured**; a resume journal in gogdl-lib is the fallback if it
turns out slow.

**Drop-safety.** No `tokio::spawn` under gogdl-lib's `downloader/` or `fs/`, and the only
`spawn_blocking` on the games path is a read-only chunk MD5, so dropping the future really stops the
transfer.

**D5 reproduced.** `sysinfo` keeps `/proc/mounts` order and `/` comes first, so gogdl-lib's
first-prefix mount match read the root filesystem for a path on a second disk (325.6 GB instead of
the disk's real 16.8 GB). Fixed as a longest-prefix match.

**`installPath` audit.** About ten readers assume a path means "installed", which decided Phase 5's
path question.

## Phase 1 — Proton version removal UI

`deleteDirectoryGuarded` (`lib/common/safe_delete.dart`) is the only recursive delete in the app. It
refuses `/`, `$HOME`, `lumenDataDir()`, their ancestors, symlinks and non-directories. Phases 5 and 7
reuse it. `directorySize` was added here for the same reason (Phase 7's dialog).

`removeVersion` deletes files first and only drops the registry entry if that worked, and it also
drops the tag's stale task, or a removed release couldn't be reinstalled. **Decision:** deleting a
custom `targetDir` is allowed, but the checkbox is unchecked by default and the dialog shows the
path. The dialog counts the pinned games rather than naming them, since `GameConfig` has no titles.

## Phase 2 — Dependency work

Done in `gogdl-lib` (`v1.2.3`) and `gogdl_flutter` (`v1.3.0`): the mount fix, `get_free_space`,
`CancelToken`, `Cancelled` variants, `getInstallSize`, and `GogError.kind()`. Things that differed
from the plan and mattered later: all *six* job streams take a required token and end with
`Cancelled` (Proton download and both save syncs too), and gogdl-lib landed the partial-extraction
cleanup (D6) itself.

## Phase 3 — Adopt the new bridge

`JobCancel` is a plain Dart class in `gog_backend.dart`; `GogdlBackend` makes the native
`CancelToken` inside the stream's lazy start and forwards `cancel()`, so a cancel before `listen`
still lands. `grep CancelToken lib` only finds `gogdl_backend.dart`, and tests never build a native
object.

**Trap:** `SavesNotifier._apply` has a `default:` branch. An unhandled `Cancelled` would have let
`onDone` mark a cancelled sync *completed*, so it maps to `failed` (nothing cancels a sync yet).
Proton download ignores `Cancelled`, so `onDone` fails its task.

**Not in the plan:** since bridge `v1.2.1` the native library is built by a Native Assets hook that
runs cargo, so Lumen's bare `debian:bookworm-slim` CI image could no longer build. CI now runs in
the bridge's prebuilt image (see Phase 10).

## Phase 4 — Cancel verification and repair

`cancel(gameId)` only fires the job's `JobCancel`. The `Cancelled` event commits
`TaskStatus.cancelled` through `_commit`, so the stale-stream guard still applies, and `onDone`
returns early for `failed` *and* `cancelled`. That is how a cancelled verification never reaches
`markInstalled`, and a cancelled repair leaves the game `downloaded`.

The handle lives in a private map, not in `ActivityTask`. `_release` removes a handle only if it is
still the registered one, or a replaced job's late terminal event would orphan the new job's handle.
`activeCount` now counts only running tasks (failed ones used to count).

**Test trap:** `addTearDown(backend.closeAll)` hangs in a widget test, because it awaits inside the
fake-async zone.

## Phase 5 — Pause, resume and cancel downloads

**Path:** `GameConfig.pendingInstallPath`, set when a download starts and moved to `installPath` by
`markInstalled`, so none of the readers that assume a path means installed had to change. Schema v2.

**Delete scope (changed from the plan):** the plan said cancel deletes the whole chosen directory.
`startDownload` now records whether the folder was empty or missing (`ownsPendingInstallDir`), and
only then may cancel remove it; a folder that is or contains another game's install is always
refused. Otherwise the dialog forces "Keep files" and says to remove them by hand.

**Mechanics:** the private map became a `_LiveJob` (`JobCancel`, a `done` completer and a
pause/discard intent), so `cancelDownload` can await the stream's end. A `Cancelled` with no intent
reads as pause, since keeping files is the safe reading. Resume is a `TaskKind.download` task with
`resumed: true` running `_runRepair`, so a failed resume goes back to `paused`, not `notInstalled`.

`startDownload` now awaits a directory listing before it starts the stream, after registering the
task so a second start is still blocked. Widget tests therefore start it inside `runAsync`.

## Phase 6 — Resume after an app exit

A persisted `downloading` with a `pendingInstallPath` loads as `paused` (no path: `notInstalled`);
a status rule, so no schema bump. **Decision:** no auto-resume on startup, because a resume starts
with a full verification pass. The Downloads page derives paused games with no task from
`gamesStateProvider` ("Paused — interrupted").

If the folder is gone, Resume commits a failed task ("The install folder … no longer exists"),
starts no job and clears nothing, so an unmounted drive can come back. `resumeDownload` re-checks
its guards after its first await, so two quick taps start one job.

## Phase 7 — Uninstall

`Uninstaller.uninstallGame` refuses while the game runs or a save sync is running, stops any job via
`DownloadsNotifier.stopJob`, deletes the folder and/or the Lumen-owned prefix (plus both logs), then
removes the whole `GameConfig` entry. A failed or refused delete rethrows with the config untouched.

**Decision (changed from the plan):** the plan deleted `installPath` unconditionally, but the picked
folder holds the game directly, so a shared folder would be wiped. Schema v3 added
`ownsInstallDir`, carried over from `ownsPendingInstallDir` by `markInstalled` (imports never own).
The dialog's "Delete game files" defaults to that flag and warns when an unowned folder is checked.
The "upload your saves first" hint is always shown, since cloud-save support isn't queryable ahead.

## Phase 8 — Downloads page actions

Dismiss (×) and "Clear finished" share `isDismissible`, which spares running and paused tasks and a
failed download of a paused game. `retryDownload` resumes a paused game through `repairDownload`,
else starts a fresh download; failed and cancelled repairs retry through `startRepair`.

A failed download now settles the game by looking at its folder (`_settleFailedDownload`): files
present → `paused` with the path kept, so Retry is a real resume; empty or missing → `notInstalled`.
It checks `ref.mounted` after that async gap (a disposed container threw in tests). `jobErrorText`
maps `GogError.kind()` to Lumen's wording (space shortfall with numbers, network, session, not
found, integrity, file system) and falls back to `gogErrorText`.

## Phase 9 — Disk space check

Install picks a folder, runs `getInstallSize` and `getFreeSpace` in parallel ("Checking space…"),
then confirms in `showInstallSpaceDialog`. **Margin:** block only when `diskBytes > free`, the lib's
own test; warn but allow under 5% headroom. A failed lookup never blocks. Import, Resume and Retry
skip the check. The bridge's free-space call returns bytes only, so the dialog says "free in
`<path>`" rather than naming the mount.

`pickDirectoryProvider` wraps `DirPicker.pick()` so widget tests can stand in for the native dialog.
**Test traps:** the dialog's three-button row overflowed at 460 px (now a `Wrap`), and a `runAsync`
wait trips google_fonts' async load.

## Phase 10 — Release and CI

The first CI run on the branch failed twice, both times in the Native Assets hook rather than in
Lumen's code:

1. The hook runs cargo with a scrubbed environment (only `HOME` and `PATH`), so `SSH_AUTH_SOCK` never
   reaches it and cargo's built-in git client can't use the agent to clone `gogdl-lib`. The fix is
   file-based: `~/.ssh/config` with the deploy key for `thinkcentre.home`, and `net.git-fetch-with-cli`
   in `~/.cargo/config.toml`.
2. GitLab deploy keys are granted per project, so the key also had to be enabled on `gogdl-lib`. The
   error for a missing permission reads "could not be found", the same as a missing project.

Not verified against the real bridge in any phase after 2 (it needs a GOG login): pause, resume,
cancel, uninstall and the space dialog were tested against `FakeGogBackend` only.
