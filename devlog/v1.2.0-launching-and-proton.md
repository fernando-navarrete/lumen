# Devlog — v1.2.0 Launching and Proton

Launch resolution, per-game logs, Stop, and the `v1.2.1`–`v1.2.5` follow-up patches from the
`v1.2.0` ROADMAP entry. Ran as eight phases plus five patches over 2026-09-22/23; kept here for the
decisions and pitfalls that aren't obvious from the diff. Ended at 266 passing tests, `flutter
analyze --fatal-infos` clean, and green CI on every tag.

## Phase 0 — Investigation

Collected `goggame-<id>.info` from 9 real installs (21 files). Always at the install root, never
nested, named after the product id — but other products' `.info` files can share the dir (a
Witcher EE `.info` sits in the Cyberpunk dir), and every DLC ships its own `goggame-<dlcId>.info`
with `playTasks: []`. So read exactly `goggame-<gameId>.info`, never glob.

`isPrimary` is usually a launcher on bigger titles (`REDprelauncher.exe`, `launcher.exe`,
`dowser.exe`, `SWB2Launcher.exe`), with the real game a separate `category: game`, `isHidden: true`
task. `path`/`workingDir` mix `\` and `/` (and one `System//witcher.exe`), all relative to the
install root.

Proton-GE layout (11-5/6/7): `wineserver` is at `files/bin/wineserver` in all three; no `dist/`
anywhere. Process-tree probing found the Windows processes, game exe included, are **not**
descendants of the spawned process — they're reparented to init in their own session — so only
`WINEPREFIX=<prefix>/pfx wineserver -k` can reach them; signalling the spawned pid or its group
cannot. Confirmed on a real game (The Witcher 3): with a launcher target, `proton run` returns
within seconds while the launcher and the game run on, so "exited" can mean "Proton returned," not
"game closed" — the main argument for Phase 2's launcher-vs-game policy. `Process.start` children
share Lumen's own process group, so a wrapper kill must target the pid only, never `-pgid`. Every
normal quit observed gave rc 0. `gamescope` wasn't installed on the dev machine; a shell-wrapper
stand-in covered the wrapper-outlives-proton case instead.

Incidental, no plan change: Proton aborts with rc 1 if `STEAM_COMPAT_DATA_PATH` doesn't exist yet
(Lumen already creates it first); running a prefix last used by another GE version logs an
"Upgrading prefix" warning but still works.

## Phase 1 — Shell-style tokenizing

`shell_words.dart`'s `splitShellWords`/`joinShellWords`: a POSIX-ish subset (single quotes fully
literal, double quotes escape `\"`/`\\`, no expansion/globbing/`~`) with the round-trip invariant
`splitShellWords(joinShellWords(x)) == x`. A `FormatException` on an unterminated quote shows as the
launch-args field's `errorText` without persisting, so the last valid value stays saved. Storage
stayed `List<String>`, so no `gamesSchemaVersion` bump was needed.

## Phase 2 — `playTasks` parsing and an off-isolate scan

**Decision:** pick the primary task if it's `category: game`; otherwise the first `category: game`
`FileTask` (hidden or not, over tasks whose exe exists on disk); otherwise the primary (the
launcher). Launchers make `proton run` return before the game does, which breaks "exited," logs and
Stop, and the stored overrides on the dev machine already pointed past them. Argument-splitting
falls back to a whitespace split if `splitShellWords` throws, rather than dropping the task — a
Windows path with a bare `\` outside quotes would otherwise be eaten as an escape (none observed).
`findExecutablesAsync` wraps the existing synchronous `findExecutables` in `Isolate.run`; it's
top-level and captures only a `String`, so it's isolate-safe as-is. The scan's skip-lists were left
alone — playTasks supersedes them for games that ship `.info`; the scan stays the fallback.

## Phase 3 — One launch-target resolver

**Decision:** `GameConfig.executable` becomes a user-override-only field. Null means "auto," which
re-resolves playTasks then the scan on every launch and is never persisted, so a game update that
changes its primary exe is followed automatically. Only a picker choice is saved. An override that
matches one of the install's GOG play tasks inherits that task's `workingDir`/`arguments`, since
only the exe path is stored. `LaunchNotifier.launchGame` ended up taking a `required LaunchTarget
target` instead of a separate `workingDir` param, since the target already carries the source that
Phase 5's log header needs. Play shows a busy state and ignores repeat taps while resolution (the
scan can take seconds) is pending. Settings' "Clear" already meant "reset to auto" under this
model, so it was relabeled rather than adding a second button.

## Phase 4 — Stale executables

A missing stored override is cleared and falls through to playTasks/the scan; the "choose another"
notice when it falls through to the picker lives inside the picker dialog itself (a new `notice` on
`PickExecutable`), not as a separate snackbar after it. A missing install directory gets its own
message ("The install folder `<path>` no longer exists") and clears nothing — distinct from a
missing single exe.

## Phase 5 — Per-game log files

**Decision:** log file only, in all builds — no mirroring to Lumen's own stdout. The footer (exit
code, duration) is written and the sink closed before the `exited`/`failed` state commits, so a
listener reading the log on the status change never sees a truncated file.

**Pitfall:** a lingering `wineserver`, or a launcher's spawned game, inherits the pipes and can hold
them open for the whole session — an unbounded wait on both pipes completing would then hold off
`exited` indefinitely. Capped by `pipeDrainGrace` (2s, `@visibleForTesting`), after which the pipes
are cancelled and the log says so. If the log file can't be opened at all (disk full, permissions),
it's logged via `logGogError` and the launch proceeds anyway — logging must never block playing.
The header deliberately includes the user's own env vars (their own values, on their own machine) —
noted in a comment so nobody "fixes" it into redaction later.

## Phase 6 — Stop a running game

`_LiveLaunch` (the `Process`, Proton/prefix paths, a `stopRequested` flag, the log, and the latest
`RunningGame`) lives in a private notifier-owned map, **not** in `RunningGame`/`LaunchState`: those
stay immutable value snapshots, and a `Process` in state would break `==` for both. Once the process
starts, every commit goes through `live.game`, so `stopGame`'s `stopping` commit and the eventual
exit commit share one identity for the existing stale-stream guard (the same one from
`devlog/v1.1.0-foundation.md` Phase 5).

`stopGame` runs `wineserver -k` with `WINEPREFIX=<prefix>/pfx` first — the only step that can reach
the game, per Phase 0 — then SIGTERMs the spawned pid after a grace period (covers a wrapper like
`gamescope` that outlives its child), then SIGKILLs after another. Never `-pgid`: Phase 0 found
`Process.start` children share Lumen's own process group. `WINEPREFIX` here is a deliberate, narrow
exception to "the only env vars the tool injects are the two `STEAM_COMPAT_*` ones" — it goes to
`wineserver` only, never to the game itself. A user-requested stop always ends `exited`, whatever
the exit code, which is also the one piece of `v1.2.3`'s policy pulled forward into this phase
(otherwise every Stop would pop the failure snackbar). While stopping, the button reads a disabled
"Stopping…"; while launching, a disabled "Launching…" (previously "Running…," which was misleading
since it couldn't be stopped yet).

## Phase 7 — Release `v1.2.0`

CLAUDE.md synced (resolution order, `LaunchTarget`/`workingDir`, logs under `<lumenDataDir>/logs`,
the `WINEPREFIX`-for-`wineserver` exception, test `overrides`); GAPS §2/§3 ticked; ROADMAP marked
done; tagged. The manual real-game checks left open across Phases 3, 5 and 6 (launch with no stored
executable, "Open log," Stop both plain and under a wrapper) were done by the user against real
installs rather than synthetic fixtures.

## P1 — `v1.2.1`: check `wineboot`'s exit code

**Decision:** on a failed `wineboot`, delete the just-created `<prefix>/pfx` rather than write an
explicit "initialized" marker file. The marker is more robust in principle, but existing
already-initialized prefixes don't have one, which would need an "assume initialized if
`pfx/drive_c` exists" migration rule for no real benefit — deleting `pfx` makes the next launch
simply retry init from scratch, which is what "half-initialized" should mean anyway.

## P2 — `v1.2.2`: validate before spawning

Added `lib/common/executable_lookup.dart` (`isExecutableFile`, `resolveExecutable`) so both the
Proton binary and, if set, the wrapper's first token are checked before wineboot, `pfx` creation, or
log rotation — a misconfiguration doesn't eat the previous run's log. The wrapper's bare-name lookup
walks `envVars['PATH'] ?? Platform.environment['PATH']`, matching what the spawned process itself
would actually see. The pre-existing "launch that fails to spawn logs why" test had relied on a
missing proton binary, which this phase now catches earlier (before any log opens) — moved onto a
working proton binary with a nonexistent `workingDir` instead, so it still exercises `Process.
start`'s own catch path.

**Wrinkle, no fix needed:** on a validation failure, the failure snackbar's "Open log" action can
still show and open an *older* log if one exists, since this launch's own log was never opened.
Acceptable — the snackbar's message is self-explanatory either way.

## P3 — `v1.2.3`: non-zero exits aren't automatically failures

**Decision:** a spawned game always ends `exited` with `exitCode` kept; `failed` is reserved for
Lumen-side failures (spawn errors, validation, wineboot), except a non-zero exit within
`immediateExitWindow` (10s, `@visibleForTesting`, measured from `Process.start`, excluding the
pipe-drain wait) of starting, which is almost always a real crash-on-start. Phase 0 only observed rc
0 normal quits, including a launcher returning rc 0 within seconds of a successful start — the
window has to tolerate that case without misclassifying it as a crash.

## P4 — `v1.2.4`: remove the `[DIAG]` prints

All 8 `[DIAG]` `debugPrint`s deleted. Of the info they carried, only the spawned pid wasn't already
in the Phase 5 log header (the header is written *before* `Process.start`) — moved into the log as
`Pid: <n>` right after the `--- game ---` marker instead of being dropped. The `flutter/foundation.
dart` import stayed; it's still needed for the file's `@visibleForTesting` annotations.

## P5 — `v1.2.5`: validate installed Proton versions on load

**Decision:** drop missing entries from in-memory state on load, but don't persist the pruning
(policy (a) of three considered — (b) prune-and-persist is permanent after one boot with a drive
unmounted; (c) keep-but-mark-missing is the most informative but touches `proton_manager.dart` for
little payoff here). A release on an unmounted drive (a custom `targetDir`) then comes back once the
drive remounts, with no extra UI needed since a missing default already falls back to Play's
existing "no Proton-GE installed" message.

Hidden entries and a hidden default are kept in a private `_unavailable`/`_unavailableDefault` on the
notifier (not in `ProtonState`) specifically so a later `_persist()` call — from `install`,
`setDefault`, or `removeVersion` — writes them back into prefs instead of silently dropping them
just because they happened to be unavailable at the moment of an unrelated write.

**Pitfall:** don't call `gamesStateProvider.notifier.clearProtonVersion` from inside
`ProtonNotifier.build()` — Riverpod forbids modifying another provider during initialization.
Per-game overrides pointing at a missing tag are left alone here; they already fail with a clear
message at Play time. The existence checks are a handful of synchronous `stat`s, so doing them
inside `build()` needed no async load path (see CLAUDE.md's `sharedPreferencesProvider` note on why
that's the wrong direction to go). New `test/helpers/fake_proton.dart` backed both the new tests and
4 existing ones (`removeVersion`, 3 in `game_action_buttons_test.dart`) that were switched from fake
`/proton/...` string paths to real fake install directories, since a path-existence check now
actually needs one.
