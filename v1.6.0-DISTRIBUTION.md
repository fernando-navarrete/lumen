# v1.6.0 — Distribution work plan

The work plan for the `v1.6.0` entry in [ROADMAP.md](ROADMAP.md): releases that users can actually
reach (GitHub, not the self-hosted GitLab), and an AppImage that updates itself in place. Both are
pipeline and packaging work; no Dart behavior changes except a small release tool. Each phase below
should fit in one short session and end with a green `fvm flutter analyze --fatal-infos` and
`fvm flutter test`, plus one commit. Phase 3 and Phase 4's tag step are the exceptions: they act on
GitHub and GitLab settings, not on this repo's tree.

The AUR package was part of this release until Phase 0 found AUR account registration closed with
no date to reopen. It is [deferred](#deferred-the-aur-package) with its Phase 0 findings kept, and
resumes as its own work once an account can be made.

Tick each checkbox as it's done. If a phase turns out bigger than one session, split it here before
starting, not halfway through.

## Branching

`main` is protected (see [devlog/ci-cd-merge-requests.md](devlog/ci-cd-merge-requests.md)): nobody
pushes to it, and every change lands through a merge request. This release has no long-lived branch.
Each group of phases gets a short-lived branch and one MR, merged semi-linearly, with the source
branch deleted on merge.

- **MR grouping** (two MRs for the whole release):
  - `feat/v1.6.0-github-release`: Phases 0–2. This plan file (Phase 0's commits), AppImage update
    information, and the `github-release` job. It merges before Phase 3, which needs the job's tool
    and the token on `main`.
  - `release/v1.6.0`: Phase 4 (docs, CHANGELOG, version bump), plus Phase 3's session-log lines.
    Phase 3 itself happens between the two MRs and commits nothing on its own. The tag follows this
    MR's merge.
  Each MR leaves `main` releasable. `pubspec.yaml` stays at `1.5.2` until Phase 4.
- Each phase is still one commit on the MR's branch, so the merge commit shows the phases underneath.
  Use squash only for an MR whose branch has red or revert commits.
- The MR pipeline runs lint, test and scan on the branch. Still run `analyze` and `test` locally every
  phase. The new tag-only job gets a **manual, non-blocking dry run on MRs** (as `package` has), so
  it is proven once before a tag depends on it.
- Phase 4 tags `v1.6.0` on `main`'s merge commit after its MR merges. That tag pipeline is the first
  real run of `github-release` from CI.
- A `v1.5.x` hotfix is the only case that uses the cherry-pick path in SECURITY.md ("Branches and
  hotfixes"). Once `github-release` exists, a hotfix tag on an older minor must not become GitHub's
  "latest" release (Phase 2), or AppImage auto-update would move users backwards.

### Opening merge requests: push options only

**Every MR in this plan is created by the push that first publishes its branch, using GitLab push
options.** No "New merge request" button in the web UI, no `glab mr create`, no API call. A branch
pushed without `merge_request.create` gets no pipeline at all (pipelines run only for MRs and tags),
so it would sit untested; if that happens, open the MR with a second push carrying the options, not
from the UI.

Before the first push, rebase onto `origin/main` (semi-linear merges require it anyway):

```bash
git fetch origin
git rebase origin/main
git push -u origin feat/v1.6.0-github-release \
  -o merge_request.create \
  -o merge_request.target=main \
  -o merge_request.remove_source_branch \
  -o merge_request.title="v1.6.0 Phases 0–2: AppImage update info and GitHub releases" \
  -o merge_request.description="One line: the full description goes in the UI"
```

- **Title:** the phase range in the commit-subject style of earlier MRs (`v1.6.0 Phase 4: release
  docs and version bump`). It becomes the merge commit's subject.
- **Description:** the sections of `.gitlab/merge_request_templates/Default.md` (Summary, then the
  Checklist with each box ticked or struck through with a reason), written to a scratch file first.
  Git refuses a push option containing a newline, so the push carries a one-line description and the
  full one is pasted into the MR in the UI right after. Don't rely on the default template being
  applied to a push-created MR.
- **Draft:** if CI is wanted before the group is complete (e.g. to play a dry-run job), add
  `-o merge_request.draft` on that first push and mark it ready in the UI when the last phase is in.
  Still one MR per group.
- **Later pushes** to the same branch are plain `git push` (or `git push --force-with-lease` after a
  rebase); the MR already exists.
- Not used: `merge_request.merge_when_pipeline_succeeds`. Threads must be resolved and the dry runs
  checked before merging, by hand.

**Corrections to GAPS §4's sketch** (settled in Phase 0):
- "Upload with `--clobber` on a re-run" can't work: the repository has GitHub's *immutable releases*
  setting **on**, so a published release's assets can never change. Phase 2 creates the release as a
  draft, uploads, then publishes; a re-run against an already-published release checks the assets
  instead of replacing them. A mistake in a published release is permanent, which is why the tool
  gets a dry run and its first real run is the backfill (Phase 3), not `v1.6.0`.
- "A `gh` image pinned by digest": there is no official `gh` container image. Phase 0 chose a small
  Dart tool run in the CI image instead (option (a) below).

**Out of scope** (note in GAPS if it comes up):
- The AUR package (see [Deferred](#deferred-the-aur-package)), Flatpak, `.deb`/`.rpm`, OBS or Copr
  (GAPS §4).
- An in-app update check or notifier. Updates come from AppImageUpdate, Gear Lever or
  AppImageLauncher reading the embedded update information.
- The insecure build-host `RUNPATH` in `libflutter_secure_storage_linux_plugin.so` that Phase 0
  found (session log). It predates this release; Phase 4 records it in GAPS.
- Everything in `v1.7.0` (prefix tools, notifications, playtime, per-game `.desktop` shortcuts).

## Dependency changes

None. `gogdl_flutter` stays at `v1.5.0` and the CI image at `-r5`; nothing here touches the bridge.
The one new external piece is a GitHub token, covered by SECURITY.md's rules in Phase 2.

**Why Phase 3 backfills `v1.5.2`:** with immutable releases on, the release tool's first real run
against GitHub should be on a release nobody depends on yet, run by hand where each step can be
watched. It also means GitHub has a "Latest" release before `v1.6.0`, so `make_latest` is computed
against a real list the first time CI runs it.

## Ordering rationale

- The investigation (Phase 0) comes first. The plan hinges on facts outside this repo: whether
  `appimagetool` 1.9.1 writes the `.zsync` itself, how long the push mirror takes to deliver a tag to
  GitHub, and whether GitHub's immutable releases are on.
- Update information (Phase 1) before `github-release` (Phase 2): the job's file set is final.
- `github-release` (Phase 2) before the backfill (Phase 3): the backfill runs the same tool, so it is
  also the tool's first real run against GitHub, on a release nobody depends on yet.
- Phase 4 releases. Auto-update can only be proven end to end by the first release *after* `v1.6.0`
  (the first AppImage carrying update information is `v1.6.0` itself), so that check is an "After
  `v1.6.0`" item, not a release gate.

## Phase 2 — The `github-release` job

Files: new `tool/github_release.dart` (under option (a)) and `test/tool/github_release_test.dart`,
`.gitlab-ci.yml`, `SECURITY.md` ("Rotate secrets", "Secrets"), CLAUDE.md's CI and release paragraphs.

The tool, given a tag, the release notes file and the asset paths:

- [x] **Wait for the mirror:** poll `git ls-remote https://github.com/fernando-navarrete/lumen
  refs/tags/<tag> 'refs/tags/<tag>^{}'` (the peeled line when the tag is annotated, as
  `check_bridge_pin.sh` does) every 10 s for up to 5 min (Phase 0 measured no delay); fail if
  GitHub's tag points anywhere but `CI_COMMIT_SHA`, and fail with a pointer to Settings → Repository →
  Mirroring on timeout. This can be a shell step in the job instead of tool code; whichever reads
  better.
- [x] **Idempotent create:** look up the release by tag. None: create it as a **draft** with the notes,
  upload the AppImage, `.sha256` and `.zsync`, then publish. A draft from a failed run: replace its
  assets and publish. A published release: compare its asset names and sizes with the local files
  and succeed if they match, fail if they differ (never delete or replace a published asset; with
  immutable releases on, GitHub refuses it anyway).
- [x] **Before publishing,** check the draft's asset list (names and sizes) matches the local files:
  once published, nothing can be fixed.
- [x] **"Latest":** set `make_latest` to `true` only when the tag is the highest `vX.Y.Z` among the
  published releases, else `false`, so a `v1.5.x` hotfix after `v1.6.0` never becomes the release
  `gh-releases-zsync|…|latest|…` points at.
- [x] Never print the token; the request helper redacts the `Authorization` header from any error.
- [x] Unit tests with a fake HTTP client: create path (draft → upload ×3 → publish), re-run on a
  draft, re-run on a matching published release (no writes), mismatch fails, `make_latest` for a
  newer and an older tag, a 401/403 fails with a message naming the token's permission.

The job:

- [x] `github-release` in the `release` stage, `v\d+\.\d+\.\d+` tags only (`.release-tag-rules`),
  `needs: [release, publish (artifacts: release_notes.md), package (artifacts)]`, image `.ci-image`,
  `cache: []`. It runs after `release`, so a GitLab release always exists before the GitHub one.
- [x] `environment: { name: github-release, action: access }` like `renovate`, and
  `GITHUB_RELEASE_TOKEN` as a masked, protected variable scoped to that environment. Fail early with
  a clear message if it's unset.
- [x] **MR dry run:** a manual, `allow_failure: true` variant on MRs (no token: protected variables
  don't reach MR pipelines) that runs the tool with `--dry-run` against the latest existing GitHub
  tag: it exercises the mirror check and the "latest" computation read-only, and prints the requests
  it would make.
- [x] `.gitlab-ci.yml` header gets a `github-release:` entry; SECURITY.md's "Rotate secrets" gets the
  token (where it lives, its permission, its expiry); CLAUDE.md's release paragraph names the job.
- [ ] **After merge (settings, no MR):** create the token (Phase 0's permission, 90-day expiry), the
  `github-release` environment and the variable. Record the expiry date in GAPS §5's calendar item in
  the next MR.

**Done when:** the tool's tests pass, the MR's dry run is green, and the job's rules can only fire on
a `vX.Y.Z` tag.
